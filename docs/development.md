# LuvBox 개발 안내

현재 정식 버전은 **1.0.0**입니다. 이 문서는 현재 동작과 개발 절차를 설명합니다. 사용자 안내는 [README](../README.md)와 [사용안내](사용안내.txt), 최신 검사 결과는 [검증 기록](verification.md)을 참고하세요. 이전 개발 검토 문서는 Git 이력에 남아 있습니다.

## 준비와 실행

Windows 64비트와 Tkinter가 포함된 Python 3.12 이상을 사용합니다. 로그인 전용 파이프의 취소·시간 제한을 위해 Windows 비동기 파이프를 사용하며, 정확한 의존성 버전은 `requirements-lock.txt`의 제약으로 고정합니다. 별도 서버나 Node.js, X 개발자 API 키는 필요하지 않습니다.

```powershell
.\setup.ps1
.\.venv\Scripts\python.exe entry.py
```

`setup.ps1`은 가상환경·Python 의존성·번들 ExifTool을 준비하고 FFmpeg를 검사합니다. Python 위치를 지정하려면 `-PythonPath 'C:\경로\python.exe'`를 사용합니다. 이후에는 `run.bat`로 실행할 수 있습니다. VS Code에서는 `LuvBox.code-workspace`를 열고 `.venv/Scripts/python.exe`를 선택합니다. F5 실행 구성은 **LuvBox 앱**과 **오프라인 테스트**입니다.

Pretendard 글꼴과 FFmpeg 실행 파일은 Git LFS 대상입니다. 새 체크아웃에서 포인터 파일만 받았다면 `git lfs pull`로 실제 파일을 받습니다. FFmpeg의 확인·재현 방법은 [번들 도구 안내](../tools/ffmpeg/README.md)에 있습니다.

## 이름과 기존 데이터 호환성

화면·프로젝트 폴더·Python 패키지·실행 파일·새 데이터 경로는 **LuvBox** 이름을 사용합니다.

- Python 패키지 `luvbox`와 새 메타데이터 식별 마커
- `%LOCALAPPDATA%\LuvBox`의 설정·세션·기록·백업·캐시
- 저장 폴더의 `.luvbox` 사본과 `.luvbox-history.sqlite3`, `.luvbox-archive*.sqlite3`
- 새 DPAPI 데이터 헤더·엔트로피와 `LuvBox 자동 저장` 예약 이름

이전 이름은 호환 입력으로만 인식합니다. 이전 앱 데이터 폴더는 전체를 새 이름으로 원자적으로 옮겨 설정·암호화 세션·DB·WAL을 함께 유지합니다. 이동할 수 없거나 두 데이터 폴더에 각각 설정·로그인·기록이 있으면 안내하고 중단하며 빈 설정으로 시작하지 않습니다. 이동 뒤 예전 실행 파일이나 예약이 다시 실행되어 `XlikeSaver`에 로그·실행 결과·캐시만 생겼다면 지우지 않고 `LuvBox\legacy\XlikeSaver-<시각>`으로 옮긴 뒤 계속합니다(실행 결과 확인 표식과 중단된 임시 파일 포함). 설정·로그인·기록까지 생겼다면 앱을 열 때 사용자가 고르면 같은 위치로 옮기고, 예약 실행은 오류로 끝나지 않고 알림으로 알립니다. 이전 이름으로만 남은 손상된 기록 DB도 ‘기록 복구’가 그 파일을 읽어 살리며 원본은 그대로 둡니다. SQLite가 전혀 읽지 못하면 이전처럼 백업으로 다시 만듭니다. 기록 복구로 고칠 수 없는 이전 이름의 다른 DB 손상에는 복구를 권하지 않습니다. 이전 DB와 저장 폴더 사본은 읽기 전용 SQLite 백업으로 새 이름에 가져오고 원본은 보존합니다. 이전 암호화 형식·완료 표식·사진 안 작성자 표식·예약 이름도 인식합니다. Git 커밋 이력의 옛 이름은 다시 쓰지 않습니다.

버전은 `luvbox/__init__.py`에서 읽습니다. 현재 정식 버전 번호를 올리지 않는 수정판도 지원하며, 테마 이미지 보관본은 실행 파일 식별값을 반영해 새 빌드에서 갱신합니다. 기존 사용자 데이터를 초기화하거나 버전 문자열의 크기 비교로 마이그레이션하지 않습니다.

## 로그인과 예약

기본 연결은 별도 Edge 창입니다. 새 임시 프로필과 상속된 전용 익명 파이프로 연결하고, 로그인된 X의 정상 `auth_token`을 Windows DPAPI로 저장합니다. TCP 디버깅 포트는 열지 않으며 사용 중인 Chrome·Edge 프로필을 직접 읽지 않습니다. 완료·취소·시간 초과 때 이번 연결 시도의 창과 임시 프로필만 정리합니다. 창을 닫을 때도 작업 정리를 기다립니다.

토큰 직접 입력과 Netscape `cookies.txt`도 지원합니다. 원문 토큰·쿠키·브라우저 프로필은 로그·설정·Git·배포 파일에 넣지 않습니다. 세션은 현재 Windows 사용자 범위로 암호화해 `%LOCALAPPDATA%\LuvBox\session.bin`에 보관합니다. `cookies.txt`는 암호화되지 않은 사용자 파일이며 경로를 설정에 저장하지 않습니다.

예약 작업 이름은 **LuvBox 자동 저장**입니다. 예약은 마지막으로 저장한 설정과 DPAPI 로그인 연결을 사용하고, `confirm_each=False`로 무인 실행합니다. cookies.txt 방식은 예약을 지원하지 않습니다. 등록된 실행 파일 경로가 달라지면 앱에서 예약을 갱신합니다. 예약 실패는 알림과 실행 기록에 남기며, 같은 계정·폴더의 작업이 이미 진행 중이면 겹쳐 저장하지 않습니다.

## 저장과 다시 시작

기본값은 구분 없이 저장·계정별 폴더 끔·새 Like만 빠르게 확인입니다. 작성자별·저장일별 폴더도 지원합니다. 저장일별 폴더는 저장을 마친 한국 날짜를 사용합니다. 계정별 폴더 옵션만 바꾸면 같은 기록을 이어 쓰지만, 정리 방식을 바꾸면 방식별 archive를 사용하므로 복사본이 생길 수 있습니다.

사진은 원본, 직접 MP4 동영상은 제공된 최고 비트레이트를 고릅니다. HLS 전용 영상은 지원하지 않습니다. 영상·GIF의 개별 용량 제한은 기본 200MiB이고 0이면 제한이 없습니다. 용량 초과는 완료 기록에 넣지 않습니다.

새 Like 확인은 이미 저장한 파일이 100개 이어지면 멈춥니다. 첫 실행, 직전 중단·오류·시험 저장, 미디어 설정 변경, 외부 기록 병합 등으로 확인 범위를 확정할 수 없으면 전체 목록을 확인합니다. 건너뛴 파일은 `catalog_meta.review_pending`에 남겨 빠른 확인에서도 그 파일들까지 도달합니다. 같은 계정 사본을 합칠 때는 이 집합을 합치고, 손상된 값은 전체 확인 후 정리합니다.

부분 전송은 `.part`로 남겨 서버가 지원하면 이어받습니다. 같은 경로에서만 이어받으므로 저장일이나 정리 방식이 달라지면 새로 받을 수 있습니다. 다 받은 뒤 저장 선택·변환·파일 확정 전에 중단하면 `.luvbox-complete` 표식을 최선으로 남깁니다. 다음 실행은 크기가 같고 수정 시각 차이가 2초 이내인 완료 `.part`를 요청 없이 재사용하며, 표식에 서버의 Last-Modified가 있으면 저장 시각에 반영합니다. 이 허용치는 동기화 도구·FAT의 시각 반올림을 위한 것이며 전체 파일 해시 검증은 아닙니다.

평소 저장은 불필요한 완료 표식을 쓰지 않습니다. 표식 기록·정리 실패가 원래 중단·저장 결과를 바꾸지 않으며, 확인 경로가 잘못되었거나 다른 프로그램이 바꾼 파일에는 새 표식을 쓰지 않습니다. 표식이 없는 파일의 HTTP 416 응답은 완료로 해석하지 않고 부분 파일을 보존합니다.

## 파일마다 저장 여부 확인

**저장 전에 하나씩 확인**은 기본 꺼짐이며, 앱에서 시작한 작업 중에도 켜고 끌 수 있습니다. 미리보기에는 임시 다운로드가 필요합니다. 사진을 표시하고 영상·GIF는 무음으로 처음 최대 30초를 재생합니다. 선택은 저장·이번엔 건너뛰기·저장 안 함·이후 자동 저장·전체 작업 중단입니다.

- **이번엔 건너뛰기**는 현재 실행에만 적용합니다. 다음 실행에서 다시 확인할 수 있고, 이후 확인을 끄거나 예약 실행하면 자동 저장될 수 있습니다.
- **저장 안 함**은 계정별 숨김·중복 방지 기록을 남겨 이후 자동 저장에서도 제외합니다. 사라진 파일의 숨긴 항목에서 명시적으로 다시 받을 수 있습니다.
- 승인 전에는 최종 파일·성공 기록·archive를 만들지 않습니다. 중단·확인 오류는 임시 파일을 보존합니다. 거절 시에도 이번 작업의 임시 파일과 검증한 완료 표식만 정리합니다.

`review.py`는 세션·요청 ID와 heartbeat가 있는 제어 파일을 사용합니다. 오래되거나 손상된 메시지를 승인으로 해석하지 않습니다. 대화창은 비모달이며, 디코더가 파일 핸들을 놓은 뒤에만 worker가 이동·정리하도록 선택을 전달합니다. 미리보기를 저장 경로에서 받으므로 동기화 폴더에서는 임시 파일도 동기화될 수 있습니다.

## GIF와 출처 기록

새 GIF 트윗은 X에서 받은 MP4를 번들 FFmpeg로 변환합니다. 원본 크기 또는 긴 변 최대 720px·15fps / 480px·12fps를 고를 수 있습니다. 작은 영상을 확대하지 않으며 길이와 반복을 유지합니다. 최종 GIF와 성공 기록이 확정된 뒤 원본 MP4 임시 파일을 지웁니다. 변환 중 중단하면 완료 MP4를 남겨 로컬 변환부터 재시도합니다. 변환 실패나 변환 GIF의 용량 초과는 원본 MP4로 저장하고 안내합니다. 원본 MP4 저장 옵션도 있습니다.

ExifTool은 JPEG·PNG·WebP·GIF·MP4의 출처 URL과 제공된 작성자 핸들·숫자 ID·프로필을 기록합니다. 트윗 작성자를 사용하며 Like한 계정으로 추정하지 않습니다. 같은 폴더의 임시 복사본에 기록하고, 출처와 작성자 태그를 다시 읽어 확인한 뒤 원본을 교체합니다. 이미지·영상·음성 스트림은 재인코딩하지 않고 수정 시각과 다른 프로그램이 넣은 메타데이터를 보존합니다. Windows의 보조 데이터 스트림도 유지하며 작성자 변경 때는 앱이 실제 추가한 값만 교체합니다.

Windows 파일 점유는 전체 제한 시간 안에서 최대 약 1초 재시도하고 매번 원본 식별값·크기·수정 시각을 확인합니다. 읽기 전용·지속 권한 오류·외부 변경은 원본을 보존한 채 중단합니다. 실패 이유는 고정된 안전한 문구로만 표시하고 외부 도구의 원문 오류를 사용자 로그에 넣지 않습니다.

작업 중에는 ExifTool 하나를 상주 실행합니다. Windows에서는 번들 Perl을 직접 실행하며, 파이프 고장·시간 초과 때 실제 작성 프로세스를 종료하고 새 프로세스 방식으로 돌아갑니다. 원본은 실패 시 교체하지 않습니다. 받은 미디어의 다운로드 성공은 출처 기록 실패와 별도로 유지합니다. 출처가 이미 기록된 기존 파일에 작성자만 추가하는 작업은 기록 창 ‘파일 관리’의 **이전 파일 출처·작성자 보완**으로 실행합니다.

## 기록·사라진 파일·복구

사용 중인 DB는 이 PC의 `%LOCALAPPDATA%\LuvBox\records\<저장폴더 식별값>\<계정>\`에 둡니다. 저장 경로의 `.luvbox/<계정>/`에는 SQLite backup API와 무결성 검사로 완성한 사본만 원자적으로 내보냅니다. WAL·SHM을 동기화 파일로 사용하지 않습니다. 다른 PC에서 바뀐 정상 사본은 먼저 합치며, 잠금·읽기 오류로 합치지 못한 사본을 덮어쓰지 않습니다.

저장 폴더를 바꾸면 계정·출력 경로 잠금을 잡고 기록을 복사·병합·검증한 뒤 교체합니다. 원래 미디어와 원본 DB는 이동하지 않습니다. 이전 경로는 정확히 기록된 파일만 허용하고 신규 저장은 현재 루트 안에서만 진행합니다. 실패하면 이전 설정을 유지합니다. 이전 드라이브가 없어 새 폴더에서 시작하는 경우에는 기록을 가져오지 못해 중복 저장될 수 있습니다.

기록 목록·실행 기록은 페이지로 조회합니다. 통계는 현재 존재하는 허용 경로의 파일을 같은 경로당 한 번만 집계하고, 게시물 이력·Like 순서와 구분합니다. Like 시기는 목록에서 처음 발견한 구간이며 X가 제공한 정확한 Like 시각이 아닙니다. 본문·해시태그는 기존 목록 응답에서 기록하므로 추가 요청이 없습니다.

탐색기에서 삭제·이동한 뒤에는 **새로고침**으로 반영합니다. 마지막 경로와 사라진 시각을 남겨 복원된 파일을 다시 연결합니다. Windows 휴지통 이동은 선택·개수·용량을 확인하고, 삭제 저널과 Shell 영수증으로 결과를 검증합니다. 실패·불확실한 결과를 성공으로 간주하거나 중단된 삭제를 자동 재실행하지 않습니다.

**사라진 파일 → 다시 받기**는 명시적으로 고른 미디어만 트윗별로 요청합니다. 중단·실패하면 처리하지 못한 파일의 archive·숨김 선택을 복원하고, 성공한 파일만 현재 경로와 연결해 숨김을 해제합니다. 이 실행은 빠른 Like 확인의 완료 지점으로 사용하지 않습니다.

기록 DB 손상은 자동 초기화하지 않습니다. **기록 복구**는 손상된 DB·WAL·SHM을 먼저 별도 보관하고, 읽을 수 있는 행과 같은 저장 폴더의 검증된 백업으로 새 DB를 만들어 무결성 검사 후 교체합니다. 미디어와 archive는 보존합니다. 정상 실행 뒤에는 저장 폴더 식별값별 일일 백업을 최근 7일 치 보관합니다.

## 오류와 요청 제한

목록 요청은 최소 10초, 미디어는 최소 2초 간격입니다. 429·로그인 거부·계정 잠금·서버 오류·네트워크 오류에는 자동 재시도하지 않고 중단합니다. 제한 대기와 계정 잠금은 앱 데이터에 보관하므로 저장 폴더 변경으로 지워지지 않습니다. 게시물별 접근 불가·삭제·연령 제한은 실행 전체의 로그인 오류와 구분합니다.

디스크 부족·파일 점유·권한·DB 오류를 대체 미디어 요청으로 우회하지 않습니다. 중단·오류 전에 완료한 파일과 기록은 유지합니다. X가 제공하지 않는 과거 목록이나 삭제된 게시물을 모두 복원한다고 보장하지 않습니다. 요청 간격과 제한 대응도 비공식 API 사용의 허용이나 계정 안전을 보장하지 않습니다.

## 검사와 배포

프로젝트 루트에서 실행합니다. 테스트는 자체 임시 파일·앱 데이터를 사용하며 실제 X 다운로드는 별도 검증입니다. `tests/app_data_isolation.py`가 테스트 프로세스의 `LOCALAPPDATA`를 임시 폴더로 바꾸므로 이 PC의 실제 데이터 폴더를 옮기거나 읽지 않습니다. 기록 저장소를 만드는 새 테스트 모듈은 이 모듈을 import합니다.
기록 조회·갤러리·미리보기의 성능 개선과 재현 명령은 [성능 검증](performance.md)에 있습니다. 공유 기록·로그인 연결·미디어 처리의 보안 경계와 자동 미리보기 보완은 [보안 검토](security-review.md)에 있습니다.
후속 구조 정리·오류 재현·화면 검수는 [리팩토링 검수](refactoring-review.md)에 있습니다.

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe entry.py --self-test .test-output\source-selftest.json
.\.venv\Scripts\python.exe tools\ui_qa.py --output .test-output\ui
.\build.ps1
```

`core.check_gallery_hooks()`는 요청 전에 gallery-dl 비공개 함수의 이름과 매개변수를 확인합니다. gallery-dl을 갱신할 때는 이 검사와 미디어·이어받기·GIF·기록·로그인 회귀를 확인합니다. UI 테스트·자체 점검·화면 캡처를 동시에 실행하지 않습니다. 실제 휴지통 검사는 기본 생략되며 자체 임시 파일로 명시적으로 실행합니다.

`tools/ui_qa.py`는 예시 미디어·기록을 만들고 X 요청·실제 로그인 저장·예약 등록을 막은 상태로 라이트·다크·작은 화면을 캡처합니다. 산출물은 `.test-output/`에만 둡니다. 최신 전체 검사와 배포 검증의 범위·결과는 [검증 기록](verification.md)에 작성합니다.

`build.ps1`은 `release/LuvBox-1.0.0/`의 폴더형 실행 파일을 만들고 `LuvBox-1.0.0.zip`, `SHA256-1.0.0.txt`를 만듭니다. 실행 파일은 같은 폴더의 `_internal`이 필요하므로 폴더 전체 또는 ZIP을 제공합니다. ZIP에는 해당 빌드의 앱 소스·고정 의존성 정보·FFmpeg/ExifTool 소스와 런타임·라이선스가 포함됩니다. [제3자 라이선스](../THIRD_PARTY_NOTICES.md)와 소스 재현 자료를 제거하지 않습니다.

빌드 뒤에는 배포 ZIP의 CRC·SHA256, 소스와 실행 파일의 일치, 한글 경로에 풀어 실행한 자체 점검, 개인 설정·로그인·DB·임시 파일의 미포함을 확인합니다. `build/`, `dist/`, `.test-output/`은 개발 산출물이며 Git에 넣지 않습니다. `release/`는 배포 산출물이므로 실행 중인 앱·등록된 예약 경로를 확인한 뒤 정리합니다. 소스 수정 후 실제 변경·검증 여부에 따라 커밋·배포하며, 같은 1.0.0 수정판은 대응 소스를 배포 ZIP에 함께 제공합니다.

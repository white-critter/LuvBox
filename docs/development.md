# 개발·문제 해결 안내

## 2.7.1 기록 합치기·미리보기 안정화

- `merge_accounts_records(paths, accounts)`는 선택한 계정 전체와 대상의 변경된 사본을 임시 기록에서 검증하고 한 번에 공개합니다. 기존 `merge_account_records(paths, account)`는 단일 계정 래퍼로 유지합니다. 상대 계정의 PC 기록과 저장 폴더 사본도 읽기 전용으로 합쳐 가져옵니다.
- 합치기로 기록·완료 키가 추가되면 `catalog_meta.quick_scan_merge_run`에 실행 ID 경계를 남겨 빠른 확인 준비 상태를 무효화합니다. 이후 해당 폴더 방식의 전체 확인이 정상 완료되어야 빠른 확인을 다시 사용합니다. 같은 계정 사본을 합칠 때도 실행 ID 변경 전에 필요한 전체 확인 상태를 읽어 보존하며, 완료된 사본의 이전 경계는 가져오지 않습니다. 기존 실행·Like 통계는 유지합니다.
- `saved_media_missing`은 현재 미디어 폴더 아래에 저장한 경로가 있는지 확인합니다. 다른 계정·이전 폴더 기록만 있는 경우 아직 만들지 않은 폴더를 누락으로 보지 않습니다.
- worker는 쓰기 잠금 확보 후 폴더 누락을 재확인합니다. `JobOptions.allow_recreate_media`는 기본 False이며, GUI의 이번 실행에 대한 승인만 전달합니다. 설정과 예약 실행에는 이 승인을 복원하지 않습니다.
- 자동 갤러리·미리보기는 클라우드 전용 파일을 디코딩하지 않고 캐시를 조회합니다. 캐시는 호출 간 정리 주기와 외부 삭제·링크 경계를 확인하며, 정리 후 `<계정>.sqlite3.epoch`을 교체해 다른 프로세스의 알려진 키도 무효화합니다. 조회 연결은 읽기 전용입니다.
- 자세한 오류 재현과 최종 검증은 `docs/review-2.7.1.md`에 있습니다.

## 2.7.0 다른 계정 기록 합치기

- 기록은 `records/<출력 키>/<계정>`에 계정마다 따로 있고, 다운로드 archive도 계정·폴더 방식마다 따로입니다. 한 출력 폴더를 함께 쓰면 gallery-dl의 같은 경로 skip만 계정 사이 중복을 막습니다(저장일별은 경로가 달라 막지 못함). 공유 폴더 검색은 `restricted`라 다른 계정만 받은 파일은 이 계정 기록에 들어오지 않습니다.
- `storage.other_account_records(paths)`: 같은 출력 키의 다른 계정 기록(이 PC, 없으면 출력 폴더의 `.xlikesaver/<계정>` 사본)과 기록 수.
- `storage.merge_account_records(paths, account)`: 호출자가 계정·출력 잠금을 잡은 상태에서 실행합니다. 지금 기록을 `backups/catalog/<계정>/catalog-*/before-merge-<계정>-<시각>.sqlite3`로 남기고, 상대 기록을 백업 API로 임시 복사해 `likes`·`runs`·`catalog_meta`를 비운 뒤 `_merge_history`로 합칩니다(파일 기록·숨김 선택·트윗 본문·옛 삭제 기록). 허용 루트는 두 계정의 것을 합치고 `catalog_meta.merged_accounts`에 계정을 남깁니다. archive는 같은 이름(폴더 방식)끼리 `INSERT OR IGNORE`로 합치거나 없으면 복사합니다. 상대 계정의 원본과 미디어 파일은 읽기만 합니다. 다시 실행해도 결과가 같습니다.
- 기록 창은 전체 불러오기 때 합치지 않은 다른 계정을 찾아 알림과 **기록 합치기**를 보여 주고, `_merge_worker`가 끝나면 폴더를 다시 확인합니다. 저장 폴더가 없거나 저장 중이면 시작하지 않습니다.
- 검사는 `tests/test_account_merge.py`에 있습니다.

## 2.6.0 사라진 파일 대비

- `xlikesaver/thumbcache.py`: 계정별 SQLite(`state_directory().parent / "thumbnails" / <계정>.sqlite3`)에 (tweet_id, num, media_type)마다 150×112 WebP(실패 시 JPEG)를 둡니다. 300 MB(`LIMIT_BYTES`)를 넘으면 오래된 것부터 지웁니다. `cloud_only`는 `FILE_ATTRIBUTE_OFFLINE/RECALL_ON_OPEN/RECALL_ON_DATA_ACCESS` 파일을 읽지 않습니다. `remember`/`recall`은 예외를 내지 않습니다.
- 만드는 곳: 저장 worker가 새로 저장한 파일마다(`Recorder`, DB 오류가 나면 그 실행 동안 끔), 갤러리·작성자 사진·파일 미리보기가 디코딩에 성공할 때(`remember`), 파일 관리의 ‘작은 미리보기 저장’(`_previews_worker`). 갤러리·미리보기는 파일을 읽지 못하면 `recall`로 저장해 둔 미리보기를 보여 줍니다.
- `media.missing_since`(새 열, 기본 ''): 새로고침이 있던 파일을 없음으로 바꿀 때, `mark_metadata`가 사라진 파일의 경로를 지울 때, 옛 삭제 기록 정리 때 시각을 남깁니다. `_restore_known_paths`는 다시 연결할 때 지웁니다. `_missing` 항목에 `last_path`와 함께 들어갑니다.
- `storage.saved_media_missing(paths)`: 기록 DB에 파일 기록이 있는데 미디어 폴더가 없을 때 True. 라이브러리(`HistoryWindow._store`, 선택 작업)는 `for_storage(..., create_media=False)`로 폴더를 만들지 않고, `_load_worker`는 이때 파일 재확인(`import_legacy(refresh=True)`)을 건너뛰며 `media_offline` 안내를 넣습니다. 라이브러리의 사본 저장(`_publish`, 선택 작업)도 출력 폴더가 없으면 건너뜁니다. 메인 화면 `start`는 `_confirm_missing_media`로 묻고, 예약 실행은 `_options_from_settings`에서 ValueError로 건너뜁니다. 저장 폴더 이전(`migrate_records`)은 그대로 새 폴더를 만듭니다.
- ‘사라진 파일’의 `missing_all`은 모든 페이지 선택 상태입니다. 표 선택이 현재 페이지 전체와 달라지면 풀리고, 새로고침·숨김 보기 전환 때도 풀립니다.
- 자세한 검토와 측정은 `docs/review-2.6.0.md`에 있습니다.

## 2.5.3 메타데이터 입력·숨김 완료·중복 기록

- 상주 ExifTool 입력은 세션마다 하나의 writer가 맡고, 입력 쓰기·flush와 종료 요청에도 기존 deadline을 적용합니다. 시간 초과 때 프로세스를 종료하고 파이프 소유 스레드가 정리하도록 합니다.
- `_choice_worker`도 공통 `_finish_local_change`로 모든 잠금 해제를 시도한 뒤 결과를 전달합니다. 정리 실패가 GUI의 작업 중 상태를 남기지 않습니다.
- 새로고침은 동일 경로의 양성 파일 검사 결과를 기록 간에도 재사용합니다. 누락·오류 결과는 재사용하지 않으며 행별 조건부 UPDATE는 유지합니다.
- 중복 파일 통계는 합쳐진 작성자 이름·ID와 일치하는 행의 완료 상태만 적용합니다.
- 검토와 검증 근거는 `docs/review-2.5.3.md`에 있습니다.

## 2.5.2 새로고침 디스크 확인 줄이기

- `HistoryStore._file`은 `_media_path`가 경로를 거부했을 때만 `_linked`를 확인합니다. 허용된 경로는 `_path_in_root`가 같은(정규화한) 경로의 링크 검사를 이미 했으므로 결과가 같습니다(링크면 ‘없음’, 폴더 밖이면 `HistoryError`).
- `_import_legacy(refresh=True)`는 첫 단계에서 있는 것으로 확인한 `_file` 결과를 입력 경로별로 두고, 폴더 검색에서 같은 경로를 만나면 다시 확인하지 않습니다. 없음으로 확인된 경로는 재사용하지 않습니다.
- `_scan_files`는 정션 여부를 `os.DirEntry.is_junction()`(목록에 들어 있는 reparse tag)으로 판단합니다. Python 3.12의 실제 정션에서 `Path.is_junction()`과 같은 값을 확인했습니다.
- 측정과 검사는 `docs/review-2.5.2.md`에 있습니다.

## 2.5.1 경로 포함 검사 속도

`HistoryStore._path_in_root`의 다섯 가지 포함 검사는 `history._within`을 씁니다. Python 3.12의 `PurePath.is_relative_to`는 `other in self.parents`로 상위 경로 객체를 모두 만들어 비교하므로, 파일마다 여러 번 부르는 새로고침에서 CPU 시간의 절반 이상을 차지했습니다. `_within`은 두 경로가 절대 경로일 때 `str(path).lower()` 접두사 비교(pathlib과 같은 대소문자 처리)로 같은 결과를 내고, 그 밖에는 pathlib에 맡깁니다. `tests/test_history.py`의 `WithinTests`가 드라이브 루트·UNC·비슷한 폴더 이름·상대 경로·그리스어 끝 시그마·터키어 İ에서 pathlib과 같은 결과인지 확인합니다. 폴더 검색의 `relative_to(scan_root)`도 `parts` 자르기로 바꿨습니다. 링크 검사(`_linked`)와 파일 `stat`은 그대로입니다. 측정은 `docs/review-2.5.1.md`에 있습니다.

## 2.5.0 일반 삭제 제거·외부 파일·GIF 기록

일반 삭제 버튼·메뉴·단축키·worker·확인창과 `deletion.py`/`recycling.py`를 제거했습니다. 옛 DB의 `deletion_items`·`missing_choices`와 병합·복구·중단 정리는 호환성을 위해 유지합니다. 이 코드는 실제 파일을 삭제하지 않습니다. 이전 삭제 기록 조회와 사라진 파일 다시 받기·숨김·숨김 해제는 유지합니다.

GIF 변환은 별도 기능으로 유지합니다. 새 다운로드의 MP4 임시 파일 또는 기존 MP4의 변환 성공 후 정리만 허용하며, 성공 기록은 GIF 경로를 가리킵니다. 외부 삭제·복원 후 새로고침에서 목록·통계·미디어 식별자별 사라진 파일을 확인합니다. 일반 저장의 완료 archive는 유지하며 사용자가 선택한 다시 받기만 해당 키를 해제합니다.

선택한 다시 받기에서 예전 기록 경로의 파일이 없으면 현재 출력 경로의 기존 파일도 확인합니다. 폴더 이전 후 외부에서 복사한 사진·GIF를 실제 경로로 다시 연결하고, 이전 파일의 임베드 성공 상태를 다른 사본에 적용하지 않고 새로 확인합니다. 기존 저장 시각과 작성자 정보는 유지합니다. 재현·검증은 `docs/review-2.5.0.md`에 있습니다.

## 2.4.4 이전 경로 조회·복원·예약 결과

`media_path` 인덱스로 이전 저장 폴더의 정확한 기록 경로 조회가 DB 전체를 반복해서 검색하지 않게 합니다. 새로고침은 카탈로그의 `last_path`에 있는 파일만 검증해 복원된 경로를 연결하며, 이전 폴더 전체를 검색하지 않습니다. 경로·폴더·링크 검사와 행의 기존 갱신 시각을 확인한 조건부 쓰기로 다른 작업의 변경을 유지합니다.

예약 실행 결과와 확인 상태는 별도 파일에 원자적으로 기록합니다. GUI는 표시한 결과를 넘기며, `last-scheduled-seen/<결과 SHA256>.json`의 확인 상태가 결과와 일치할 때만 적용됩니다. 다른 실행의 확인은 서로 덮지 않습니다. 새 실행에 UUID를 넣어 같은 초에 끝난 동일한 결과도 구분합니다. 예전 `seen` 필드와 인자 없는 확인 호출은 유지합니다. 검토·측정·검증은 `docs/review-2.4.4.md`에 있습니다.

## 2.4.3 작성자 목록 지연 표시

`HistoryWindow._show_stats`는 새 통계가 오면 `_authors_stale`만 표시하고, 통계 탭(인덱스 2)이 보일 때만 `_fill_authors`로 Treeview를 다시 채웁니다. 숨어 있던 목록은 `<<NotebookTabChanged>>`에서 한 번 채웁니다. `_fill_authors`는 항상 이 표시를 지우므로 작성자 찾기 입력은 그대로 즉시 반영됩니다. 콤보박스의 작성자 선택지는 열 때 `self.stats`에서 만들므로 영향이 없습니다. 자세한 측정은 `docs/review-2.4.3.md`에 있습니다.

## 2.4.2 기록·미리보기 안정화

전체 코드를 검토해 재현된 네 가지 문제를 수정했습니다. 이전 형식의 백업 복구는 행마다 존재하는 열만 넣어 SQLite 기본값을 적용합니다. 경로 변경은 원본·대상 폴더에 새로 도착한 기록 사본을 임시 DB에서 병합한 뒤 확정합니다. 미리보기는 성공한 결과만 캐시합니다. 로컬 변경 작업은 기록 닫기·사본 저장·잠금 해제를 마친 뒤 완료 이벤트를 보냅니다.

기존 페이지 조회·통계 재사용·이미지 캐시·단일 디코더 성능 개선은 유지합니다. 자세한 재현과 검증은 `docs/review-2.4.2.md`에 기록합니다.

## 2.4.1 안내 문구

사용자에게 보이는 70자 이상 문장 42개와 로그인 방식이 바뀌어 맞지 않던 안내를 다듬었습니다. 고정 오류 문구(`_LOCAL_WRITE_ERROR`, `_RESUME_ERROR_HELP` 등)는 상수 이름과 쓰임이 그대로이며, 문구를 확인하는 검사는 같은 의미의 새 표현을 확인합니다. `AUTH_MODES`의 내부 키는 설정·검사 호환을 위해 유지하고 화면에는 ‘브라우저 로그인’으로 표시합니다.

## 2.4.0 아이콘·우클릭·Edge 로그인

`app_icon.install`은 메인 창과 새 Toplevel의 Windows 아이콘을 설정합니다. `assets/icons`는 실행 파일 리소스와 런타임에 모두 포함됩니다. PNG에서 ICO 재생성은 `tools/build_icon.py`로 합니다.

우클릭 메뉴는 기존 버튼의 사용 가능 상태와 함수를 재사용합니다. 파일 열기는 포커스 행, 여러 파일 작업은 기존 선택 전체를 대상으로 합니다. 통계의 대표 이미지 메뉴는 경로·트윗·작성자를 열 때의 값으로 고정합니다.

Edge 전용 로그인은 비어 있는 loopback 포트를 골라 `/json/version`의 검증된 브라우저 WebSocket 주소를 사용합니다. 10초 뒤 X 로그인 문서가 비어 있고 입력 칸이 없으면 한 번 다시 불러옵니다. 별도 프로필에 속한 프로세스만 정리하고, 임시 프로필 경로를 강제로 덮어쓰는 정책은 실행 전에 확인합니다. 검토와 실제 화면 검증은 `review-2.4.0.md`에 기록했습니다.

`_merge_media`는 갱신 시각이 같은 경우 명시적 삭제 상태를 최신 상태로 고릅니다. 두 기록 모두 실제 파일이 없을 때 삭제 전 경로를 채워 넣지 않으며, 실제로 존재하는 복원본이나 다른 위치의 사본은 우선합니다. 같은 초 안의 저장·삭제·반복 병합을 시각을 고정한 검사로 재현합니다.

## 2.2.2 라이브러리 속도

- `HistoryWindow.refresh(view_only=True)`: 페이지·검색·종류·정렬·기간·작성자·페이지 크기 변경은 직전 `overview`(요약·통계·사라진 파일)를 worker에 넘겨 재사용하고, 목록·실행·삭제 기록 페이지만 다시 읽습니다. 새 위치, 폴더 재확인, 대기 중이던 새로고침, 작업 완료, 저장 중 자동 갱신, 새로고침 버튼은 언제나 다시 계산합니다.
- `HistoryStore.records`는 행 번호(rowid)만으로 정렬·LIMIT을 먼저 정하고, 고른 행에만 likes·tweets를 붙입니다. 정렬 키가 기본 키를 모두 포함해 두 단계의 순서가 같습니다. Like 순서와 본문 검색일 때만 고르는 단계에서도 다른 표를 붙이고, 개수는 검색어가 없으면 `media`만 셉니다.
- `_unique_files`는 기록이 하나뿐인 파일(대부분)에 일반 병합과 같은 결과를 내는 빠른 경로를 쓰고, `_file_snapshot`은 Row 객체 대신 튜플과 열 이름으로 dict를 만듭니다. 월별 통계는 서로 다른 앞 7글자마다 한 번만 형식을 검사합니다.
- 저장 중 라이브러리 자동 갱신 간격은 마지막 전체 불러오기 시간의 3배(2~30초)입니다(`auto_refresh_delay`).

측정(기록 12만 개, 이 PC): 페이지 이동 약 3.3초 → 0.2초, `overview` 2.69초 → 1.55초, 첫 페이지 조회 0.58초 → 0.19초, 마지막 페이지 1.25초 → 0.31초.

## 2.2.1 안정화

- 메인 창은 작업 프로세스의 이벤트 파일을 바이트로 읽고 줄 단위로만 해석합니다. 텍스트 모드 `read()`는 쓰는 중인 한글 UTF-8 중간에서 `UnicodeDecodeError`를 일으켜, 그 실행의 나머지 진행 이벤트를 모두 잃었습니다.
- `HistoryStore` 초기화는 옛 행에 빈 `source_url`이 있을 때만 UPDATE를 실행합니다. UPDATE는 맞는 행이 없어도 쓰기 잠금을 기다리므로, 저장·삭제가 쓰는 동안 화면 스레드의 파일 열기와 미리보기 확인이 최대 5초(busy timeout) 멈추거나 실패했습니다. 평소 열기는 이제 읽기만 합니다.
- 기록 복구는 `repair_active`로 표시합니다. 라이브러리 창·메인 창을 닫으면 복구가 끝난 뒤 닫고, 그동안 저장·기록 이전을 시작하지 않습니다. 메인 창은 라이브러리 작업 상태를 `_library_job_active()` 하나로 확인합니다.
- `deletion_items(tweet_id,num,media_type)` 색인으로 라이브러리의 삭제 제외 조건이 기록마다 삭제 기록 전체를 훑지 않습니다. `_apply_deleted_path`는 파일 이름이 트윗 ID로 시작한다는 점을 이용해 같은 트윗의 행만 기본 키로 조회합니다.
- 폴더 재확인(`import_legacy`) 끝에 `_release_restored_choices`가 휴지통에서 원래 경로로 돌아온 파일을 찾아, 그 삭제가 같은 시각으로 기록한 ‘다시 받지 않기’만 해제합니다. 이후 다른 사본의 삭제나 사용자의 이후 선택은 시각이 달라 유지됩니다.

## 2.2.0 삭제 기록 호환

일반 파일 삭제 실행 코드는 2.5.0에서 제거했습니다. SQLite `deletion_items`의 옛 기록과 재다운로드 선택은 사본 병합·DB 복구에도 포함됩니다. pending 의도는 정상 작업 잠금 안에서 `reconcile_deletions`로 확인하며 실제 삭제를 다시 실행하지 않습니다. 복원한 파일의 삭제 당시 선택만 기존 정책대로 해제하고 이후 사용자가 지정한 선택은 유지합니다.

Windows ExifTool 런처만 종료하면 실제 Perl 작성 프로세스가 파이프를 계속 보유할 수 있습니다. 번들 `perl.exe`와 `exiftool.pl`을 직접 실행해 timeout이 실제 작성 프로세스를 종료하도록 했습니다. 상대 ASCII 스크립트와 번들 cwd로 한글·이모지 설치 경로를 지원하고, stdout/stderr는 reader가 EOF 뒤 닫습니다. 종료 스레드는 최대 0.5초만 reader를 기다리므로 BufferedReader의 잠금으로 무한 대기하지 않습니다. 같은 번들·라이선스를 그대로 사용하며 제3자 runtime 파일은 바꾸지 않습니다.

## 로그인

기본은 전용 Edge 창 로그인입니다(`browser_login.py`). 임시 사용자 프로필과 무작위 로컬 디버깅 포트를 사용하며 기존 브라우저 프로필은 열지 않습니다. X 로그인 후 `Storage.getCookies`에서 정상적인 x.com `auth_token`만 골라 기존 `save_auth_token`으로 DPAPI 저장합니다. 완료·취소·시간 초과 때 해당 창을 닫고 이번 시도의 임시 프로필만 정리합니다. 다른 앱 인스턴스의 임시 프로필은 지우지 않습니다. 강제 종료하면 임시 프로필이 남을 수 있습니다.

GUI 작업 스레드는 Tk 객체를 보유하지 않고 queue로 결과만 전달합니다. 취소 후 worker 정리가 끝나기 전에는 다시 연결하거나 저장을 시작하지 않습니다. 앱을 닫아도 worker 정리를 기다립니다.

토큰 직접 입력과 Netscape cookies.txt도 지원합니다. 일반 브라우저에서 정상 로그인된 본인 X 세션을 사용합니다.

토큰은 X 탭에서 F12 → Application → Cookies → https://x.com → `auth_token`의 Value를 복사해 앱에 저장합니다. 토큰 이름이나 비밀번호를 입력하지 않습니다. 현재 Windows 사용자 범위로 DPAPI 암호화해 `%LOCALAPPDATA%/XlikeSaver/session.bin`에 저장합니다. 원문을 로그·설정·배포본에 넣지 않습니다. [Chrome 쿠키 화면](https://developer.chrome.com/docs/devtools/application/cookies/)

cookies.txt는 Netscape 형식으로 X 사이트의 쿠키만 내보내 지정합니다. 이 파일은 암호화되지 않으므로 직접 보관해야 합니다. 사용 중인 Chrome/Edge 프로필 직접 읽기는 제공하지 않습니다. [gallery-dl 쿠키 안내](https://github.com/mikf/gallery-dl/blob/v1.32.15/README.rst#cookies)

## 파일·기록

미디어 경로와 기록 경로를 분리합니다. 미디어는 선택한 저장 방식에 따라 저장하고, 사용 중인 DB는 이 PC의 `records_root()/<저장폴더이름-경로해시12>/계정명/`(`StoragePaths.record_dir`, 실제로는 `%LOCALAPPDATA%/XlikeSaver/records`)에 둡니다. `저장 경로/.xlikesaver/계정명/`(`snapshot_dir`)에는 `publish_snapshot`이 SQLite backup API로 만든 사본(무결성 검사, DELETE 저널)을 임시 파일 뒤 `os.replace`로 통째로 바꿔 둡니다(동기화 프로그램이 잠깐 잡고 있으면 재시도). 예전 버전의 -wal/-shm은 지웁니다. `record_dir/snapshot.json`에 이 PC가 마지막으로 쓰거나 읽은 사본의 크기·수정 시각을 남기고, 보호된 열기(작업 프로세스·저장 폴더 초기화)에서 사본이 달라졌으면 `_merge_database`로 합칩니다(archive는 합집합, 기록은 더 나은 행). 손상된 사본은 건너뜁니다. 로컬에 DB가 없으면 `prepare_storage`가 사본(또는 예전 계정 폴더)을 읽기 전용 backup으로 가져옵니다. 저장 경로는 기록 루트 안에 둘 수 없고, 저장 경로가 앱 데이터를 포함해도 기록·백업 폴더는 미디어로 취급하지 않습니다. `.xlikesaver-history.sqlite3`는 상세 내역, `.xlikesaver-archive*.sqlite3`는 파일별 중복 방지 기록입니다. 같은 저장 루트에서 계정별 폴더 옵션만 바꾸면 기존 기록을 사용하며 알려진 파일의 원래 경로를 유지합니다. 작성자별·저장일별·구분 없이 정리 방식은 각각 별도 archive를 사용하므로 방식을 바꾸면 복사본이 생길 수 있습니다.

이전 계정 폴더의 DB는 SQLite 읽기 전용 backup으로 새 기록 폴더에 복사합니다. 기존 DB를 덮어쓰거나 미디어를 옮기지 않습니다. 공유 폴더에서 다른 계정의 파일을 무조건 통계에 포함하지 않습니다. 동일 저장 루트의 다운로드·출처 기록 작업은 파일 충돌을 피하도록 겹쳐 실행하지 않습니다.

앱은 계정별 마지막 기록 위치를 설정의 `record_locations`에 보관합니다. 폴더 선택 또는 Enter·저장 시작·기록 보기를 누른 후 경로가 바뀌면 원본과 새 경로를 잠그고 SQLite 읽기 전용 backup으로 기록을 준비합니다. 목적지에 기록이 있으면 archive·상세 내역·실행 이력을 합쳐 검증한 후 계정 기록 폴더를 교체합니다. 중간에 종료되면 이전 기록 폴더를 복구하며, 실패한 경우 이전 설정을 유지합니다. 요청 제한 중에도 이 로컬 작업은 가능하며 제한 대기 기록은 유지합니다.

기존 미디어를 이동하지 않습니다. 이전에 선택한 루트와 정확히 기록된 파일 경로만 파일 열기·출처 기록에 허용하고, 신규 다운로드는 현재 저장 루트 안에서만 진행합니다. 여러 번 경로를 바꾸거나 이전 위치로 돌아와도 알려진 파일·실행 기록이 중복되지 않게 합칩니다. 이전 폴더가 없으면 사용자에게 새 폴더에서 시작할지 확인합니다. 동의한 경우 계정·목적지 잠금을 확보해 기존 목적지 기록을 보존하며 초기화합니다. 이전 기록을 가져오지 못하므로 중복 다운로드될 수 있습니다. 이전 드라이브를 다시 연결해 앱에서 선택하면 양쪽 기록을 합칠 수 있습니다. 손상된 DB나 경로 검증 실패는 이 선택으로 우회하지 않습니다. OS 잠금은 이 앱의 작업끼리 보호하며, 다른 도구가 DB를 수정하는 동안의 임의 변경까지 제어하지는 않습니다.

파일·실행 목록은 페이지당 50/100/200개를 조회합니다. 파일 검색 조건을 적용한 총수와 페이지 목록은 짧은 SQLite 읽기 트랜잭션에서 함께 읽고, 범위를 벗어난 페이지는 마지막 페이지로 보정합니다. 파일 정렬에는 저장 방식과 미디어 유형을 포함해 같은 시각의 행도 안정적으로 나눕니다. 조회 중 검색이 바뀌면 이전 결과를 표시하지 않고 최신 조건을 다시 조회합니다.

SQLite WAL과 `synchronous=FULL`을 사용합니다. 기록 창의 폴더 재확인은 파일을 트랜잭션 밖에서 읽고 200건씩 짧게 커밋하므로, 같은 기록 DB를 쓰는 다운로드 worker가 잠금 대기로 실패하지 않습니다. 다운로드 중에는 기록 창이 폴더 재확인 자체를 건너뜁니다. 비정상 종료 기록은 다음 worker가 계정 잠금을 확보한 뒤 중단됨으로 정리합니다. 모르는 종료 시각을 만들어 넣지 않습니다. 하드웨어 고장·정전의 완전 복구, 손상 DB 자동 복구, 완료 파일 전체 해시·디코더 검증은 제공하지 않습니다. 옮기거나 지운 완료 파일도 중복 방지 기록에 남아 있으면 자동으로 다시 받지 않습니다.

과거 archive에서 정보가 부족하면 경로나 저장 시각을 임의로 만들지 않습니다. 파일 크기는 확인 가능한 것만 합산합니다. 게시물 ID에서 계산한 게시일은 추정으로 표시합니다. Like 시각과 실제 저장 시각은 별개입니다. [Like 시각 기능 검토](like-time-options.md)

출처 메타데이터는 JPEG·PNG·WebP·GIF·MP4의 XMP Source/Description 및 MP4 ItemList Comment에 기록합니다. 기존 설명과 다른 언어 값은 유지합니다. 같은 폴더의 임시 복사본을 수정하고 URL을 다시 읽어 확인한 뒤 원본을 원자적으로 교체합니다. 실패 시 원본과 완료 기록을 보존합니다. 수정 시각은 유지하며 이미지·음성·영상 스트림을 재인코딩하지 않습니다. 다운로드와 기존 파일 출처 기록 동안에는 ExifTool을 `-stay_open`으로 하나만 띄워 재사용합니다(호출당 약 0.2초 → 0.01초). 상주 프로세스가 멈추거나 시간을 넘기면 종료하고 호출마다 새 프로세스를 쓰는 방식으로 돌아갑니다. 탐색기에서 모든 형식의 출처를 클릭할 수 있다는 보장은 없으므로 앱의 트윗 열기를 사용할 수 있습니다.

작성자의 X 핸들은 `XMP-dc:Creator`에 `@handle`, 프로필 URL은 `XMP-dc:Relation`에 저장합니다. 숫자 사용자 ID와 작성자 식별 마커는 배열 태그 `XMP-xmp:Identifier`에 저장하며 Description과 MP4 Comment에도 읽기 쉬운 설명을 추가합니다. Like한 계정이 아니라 트윗 작성자 정보(gallery-dl `author.name`, `author.id`)를 사용합니다. Creator·Relation·Identifier에서 다른 프로그램이 넣은 값은 보존합니다. 작성자 핸들이나 ID가 바뀌면 실제로 앱이 추가한 예전 `@handle`·프로필 URL·설명 줄만 지우고 새 값으로 바꿉니다. 핸들·숫자 ID 형식이 아닌 작성자 값은 알 수 없는 작성자로 보고 출처만 기록합니다. `metadata.read_author()`로 작성자·숫자 ID·프로필을 확인할 수 있습니다. 상세 DB는 `author_id`, `author_metadata_status`를 별도로 보관합니다. 저장 실행은 새로 받은 파일과 출처 기록이 아직 없는 기존 파일만 다시 씁니다. 출처가 이미 기록된 기존 파일은 작성자만 위해 다시 쓰지 않고 DB만 갱신합니다. 전체 확인이 라이브러리 전체를 다시 쓰거나 클라우드 동기화가 전체를 다시 올리는 일을 막기 위해서입니다. 이런 파일은 기록 창의 기존 파일 작업에서 한 번에 작성자를 추가하고, 실패하면 다시 시도할 수 있습니다. 기존 파일 작업은 알려진 로컬 작성자만 사용하며 모르는 작성자를 X에서 조회하지 않습니다.

작성자 항목을 교체할 때는 실제로 앱이 추가한 값의 별도 소유 기록을 확인합니다. 단순 작성자 식별 마커는 값의 소유 증거로 사용하지 않습니다. 이전 버전처럼 소유 기록이 없는 Creator·Relation·설명·Comment 값은 보존하고 최신 작성자를 함께 기록합니다. 기존 설명의 줄 구분자도 유지합니다. 대소문자 변경도 DB에서 처리 대기로 남기며, 과거 작성자 오류를 보류한 실행은 이번 기록 실패로 집계하지 않습니다.

## 제한·예외 처리

- 사용자 중단·창 닫기: 통신이나 메타데이터 처리가 끝나기를 기다리고 worker를 정리합니다. 완료한 파일은 유지합니다. 받던 사진의 다른 크기를 요청하지 않으며, `.part`는 다음 실행에서 서버 지원 시 이어받습니다.
- 네트워크·타임아웃·서버 오류: 자동 재시도 없이 멈춥니다. 회복 후 수동으로 시작합니다.
- HTTP 416: 완료 처리하지 않고 부분 파일을 보존합니다. 반복되면 안내된 `.part`만 삭제하고 다시 시작합니다.
- 디스크 부족·쓰기 권한·파일 잠금·DB 오류: 다음 파일이나 대체 요청을 진행하지 않고 중단합니다. DB를 자동 초기화하지 않습니다.
- 영상 용량 초과: 완료 기록에 넣지 않습니다. 제한을 늘리거나 0으로 바꿔 나중에 받을 수 있습니다.
- 출처 기록 실패: 받은 미디어는 보존합니다. 기록 창의 ‘출처·작성자 기록’으로 다시 시도합니다.
- 정상 완료·저장 0: 새 미저장 파일이 없으면 정상입니다. 현재 파일 퍼센트는 전체 Like 완료율이 아닙니다.

현재 비공식 X 내부 GraphQL API와 로그인 세션을 사용합니다. X는 사전 동의 없는 스크래핑 및 비공식 자동화에 제한을 둘 수 있습니다. 아래 조치는 과도한 요청을 줄이며 정책상 허용이나 계정 안전을 보장하지 않습니다. [X 이용약관](https://x.com/en/tos), [자동화 규칙](https://help.x.com/en/rules-and-policies/x-automation)

- 목록 요청 최소 10초, 미디어 요청 최소 2초 간격.
- 429·로그인 거부·계정 잠금·서버 오류에 재시도 없이 중단. 미디어 404에는 다른 제공 크기 확인 가능.
- 서버 reset/Retry-After 중 늦은 시각에 5초를 더해 대기. 안내가 없으면 15분 대기.
- 남은 API 요청이 5회 이하이면 다음 요청 전에 멈춤.
- Windows 사용자 폴더에 입력 계정별 대기 기록·실행 잠금 보관. 저장 폴더 변경·앱 재시작으로 지워지지 않음.
- 빠른 확인은 이미 저장한 파일이 100개 연속이면 목록 조회를 멈춤. 직전 실행이 정상 종료되지 않았거나 미디어 설정이 바뀌면 자동으로 전체 확인.
- 정상 작업을 반복해도 목록 조회 요청은 누적됨. 다른 PC·프로그램·브라우저 요청은 제어하지 못함.
- 국가 제한·연령 제한·볼 수 없는 미디어·작성자 정보 없음 같은 게시물별 경고는 안내로만 표시하며, 실행 실패 이유나 로그인 문제로 보고하지 않음.

HTTP 429와 계정 정지는 별개입니다. 잠금·보안 확인이 뜨면 X에서 직접 확인합니다. 공식 API 요청 한도를 내부 API에 그대로 적용하거나 특정 간격이 안전하다고 단정하지 않습니다. [공식 X API 요청 제한](https://docs.x.com/x-api/fundamentals/rate-limits)

## 배포

실행에는 `release/XlikeSaver-<버전>/XlikeSaver-<버전>.exe`와 같은 폴더의 `_internal`이 함께 필요합니다. 앱 폴더째 보관합니다. 이름에 버전이 붙어 있어 이전 exe를 실행 중이어도 새로 빌드할 수 있습니다. 재배포에는 `XlikeSaver-<버전>.zip`의 소스·라이선스도 함께 제공합니다. 사용자 세션이나 cookies.txt를 배포하지 마세요. ExifTool/Perl 전체 도구와 의존성 라이선스를 포함합니다. [의존성 안내](../THIRD_PARTY_NOTICES.md)

`build/`는 PyInstaller 중간 파일이며 지워도 됩니다. 예약 실행은 등록한 exe 경로를 그대로 실행하므로, 새 버전을 처음 열면 앱이 예약을 그 버전으로 바꿀지 묻습니다.

## 자동 저장 예약

`scheduled.py`는 Windows PowerShell의 ScheduledTasks 모듈(`Register-ScheduledTask`)로 매일 작업을 등록·해제·조회합니다. 스크립트는 고정 문자열을 `-EncodedCommand`로 넘기고, exe 경로·시각 같은 값은 환경 변수(`XLS_*`)로만 전달합니다. 설정은 `StartWhenAvailable`(놓친 실행 즉시 실행), `AllowStartIfOnBatteries`·`DontStopIfGoingOnBatteries`, `MultipleInstances IgnoreNew`, 실행 제한 12시간이며, 현재 사용자로 로그인해 있을 때 실행됩니다. PowerShell 출력은 화면에 보이지 않고 고정 안내만 표시합니다.

`run_saved`는 결과를 `%LOCALAPPDATA%/XlikeSaver/last-scheduled.json`에 남깁니다. 실패하면(같은 계정·폴더의 다른 저장이 실행 중이던 경우 제외) 테마를 따른 알림 창을 맨 위에 띄우고, 앱은 다음 실행 때 아직 보지 않은 실패를 상단에 알립니다. 설치본(exe)은 시작할 때 작업을 조회해 다른 exe로 등록돼 있으면 한 번 갱신을 묻습니다(설정의 `schedule_prompted`).

## Like 순서와 시기

X는 Like 시각을 주지 않습니다(gallery-dl의 `date_liked`도 X 변경으로 제거됨). 기록 DB의 `likes` 표는 트윗마다 `like_key`(클수록 최근 Like), `liked_before`(처음 발견한 실행의 시작 시각), `liked_after`(하한, 알 수 없으면 NULL)를 둡니다. 실행은 Like 목록을 최근 Like부터 훑으며(`core.handle_directory`), 이미 순서가 있는 트윗을 기준점으로 삼아 그 사이에 새로 발견한 트윗의 키를 보간합니다(`history.LikeOrder`). 목록 맨 위에서 기준점 전에 나온 새 트윗은 모든 키보다 위에 두고, Like를 기록하기 시작한 뒤 정상 종료된 직전 실행의 시작 시각을 하한으로 둡니다. 기준점 사이나 마지막 기준점 아래에서 새로 나온 트윗은 예전에 보이지 않던 오래된 Like일 수 있어 하한을 두지 않습니다. 기록 이전 시 `likes`는 대상에 없는 트윗만 합칩니다.

## 성능

- 빌드는 PyInstaller **폴더 빌드**(`--onedir`)입니다. 한 파일 빌드는 실행할 때마다(앱, 저장 작업 프로세스, 예약 실행) 약 40MB를 임시 폴더에 풀어 시작에 약 4초가 걸렸습니다.
- 테마의 둥근 이미지는 **불투명**하고 크게 만듭니다. Windows의 Tk는 반투명 이미지를 다시 그릴 때마다 소프트웨어로 합성하므로, 모서리를 컨트롤이 놓인 배경(창/카드)에 미리 섞은 두 벌(`Soft.*`, `Soft.*.card`)을 두고 `_bind_surfaces`가 카드 위 컨트롤에 `.card` 레이아웃을 줍니다. 가운데를 늘린 큰 이미지라 카드·버튼이 몇 장의 타일로 그려집니다. 창 크기 조절 한 단계가 메인 514→185ms, 기록 783→334ms로 줄었습니다.
- 이 이미지(약 110개)를 그리는 데 Python에서 약 0.5초가 걸려, 설치본(exe)은 `_draw_assets`의 결과 PNG를 `%LOCALAPPDATA%/XlikeSaver/cache/theme-<버전>-<모드>-<키>.zip`에 보관합니다. 키는 버전·모드·색상표(소스 실행은 theme.py 내용 포함)의 해시입니다. 같은 버전의 라이트·다크 두 벌을 남기고 다른 버전의 보관본은 지우며, 읽지 못하면 다시 그립니다. 소스·테스트 실행은 디스크 보관본 없이 메모리에만 둡니다. exe 창 표시까지 1.15→0.69초(첫 실행 제외), 테마 전환 0.53→0.07초.
- 폴더 재확인(`import_legacy`)은 폴더마다 한 번만 링크·실제 경로를 확인하고(파일 자체의 링크 여부는 매번), 바뀌지 않은 기록은 다시 쓰지 않습니다. 1.1만 건 Google Drive 폴더에서 14.4초→2.6초. 이 확인은 경로를 기록만 하며, 쓰기·열기 전에는 파일마다 다시 확인합니다.
- 작업 중 실행 진행 상황은 2초마다(마지막에는 항상) 기록하고, 이미 있는 파일의 기록이 바뀌지 않았으면 쓰지 않습니다. 트윗당 처리 비용(X 요청 간격 제외)이 7.3ms→2.9ms. 디스크에 반영(fsync)하는 커밋이 줄어 동기화 폴더에서 효과가 큽니다.

## 기록 DB 복구

`recovery.salvage`는 SQLite가 읽지 못하는 표를 파일 형식대로 루트 페이지부터 따라가며 셀을 직접 해석합니다(넘침 페이지 포함, 깨진 셀은 건너뜀). `rebuild_history`는 새 스키마에 살린 행을 넣고(같은 기록은 rowid가 가장 큰 최신 판) 최근 백업에만 있는 행을 더한 뒤 무결성 검사를 통과해야 설치합니다. `repair_history`는 원본·WAL·SHM을 앱 데이터 backups에 먼저 복사하고, 복사본에서 WAL을 체크포인트한 뒤 재구성합니다. `backup_catalog`는 실행마다 SQLite backup API로 일별 복사본을 만들고 `quick_check`를 통과한 것만 남깁니다. `CatalogDamaged`는 SQLITE_CORRUPT/NOTADB에서만 발생합니다.

## 본문·작성자·통계·모아보기

`tweets` 표는 트윗마다 본문(줄바꿈은 공백, 제어 문자 제거, 최대 5,000자)과 해시태그(`#태그` 공백 구분)를 둡니다. 실행이 트윗을 지날 때(`handle_directory`) 50개씩 모아 기록하고 끝날 때 나머지를 씁니다. 검색은 `media`에 `likes`·`tweets`를 LEFT JOIN 해 작성자·트윗 번호·파일명·본문·해시태그를 찾습니다. 작성자 필터는 `author=?`(대소문자 무시, 정확히 일치)입니다.

`HistoryStore.statistics()`는 작성자 순위(파일 수·트윗 수·최근 게시일)와 게시월·저장월·Like 발견월(하한을 아는 새 Like만) 개수를 돌려줍니다. `charts.MonthlyBars`는 한 색(라이트 `#526fe8`, 다크 `#6f88f2`, 두 배경 대비 검증)의 막대그래프를 Canvas에 그리고 빈 달을 0으로 채우며 36개월이 넘으면 해마다 묶습니다. 테마 전환 시 `theme_redraw`로 다시 그립니다.

`gallery.ThumbnailGrid`는 현재 페이지의 섬네일을 하나의 백그라운드 스레드에서 만들고(기록이 허용한 경로만, 최근 240개 캐시), Tk 이미지는 UI 스레드에서만 만들고 놓습니다. 타일을 고르면 표의 같은 기록이 선택됩니다.

## 로컬 미디어와 테마

`preview.py`는 Pillow로 사진/GIF 첫 프레임, 번들 FFmpeg로 동영상 첫 프레임을 읽습니다. 소형 메모리 캐시와 단일 디코더가 최신 선택만 처리하며 창을 닫으면 결과를 버립니다. 기록이 허용하는 로컬 경로만 읽고 네트워크 프로토콜을 사용하지 않습니다.

`media.py`는 MP4 다운로드 완료 후 두 번의 palettegen/paletteuse 처리로 원본 크기의 GIF를 만들고, 최종 GIF와 archive 기록이 확정된 뒤 원본 임시 파일을 정리합니다. GIF는 256색으로 제한되며 10ms 시간 단위를 사용합니다. 중단 시 `.mp4.part`와 크기/수정시각을 담은 완료 표식으로 로컬 재시도합니다. 변환 실패나 GIF 용량 초과가 실행 전체를 막지 않도록, 그 파일은 원본 MP4 경로로 확정해 archive에 기록하고 경고만 남깁니다. 완료 표식이 있는 MP4가 낮아진 용량 제한을 넘으면 일반 용량 초과처럼 건너뛰고 임시 파일을 지웁니다. 기존 저장된 MP4의 미디어 ID와 archive 키는 유지합니다. `gif_format="mp4"`이면 변환하지 않고 원본 MP4로 확정합니다.

`GIF_SIZES`의 `720`/`480` 프리셋은 `scale`로 긴 변을 상자 안에 맞추고(확대 없음) `-fpsmax`로 초당 장면 수를 제한합니다. 번들 FFmpeg에는 `fps` 필터가 없고, 출력 정속 모드는 끝에 최대 2장을 더 남겨 루프마다 멈칫하므로 첫 패스의 `Duration`을 읽어 `-t`로 원본 길이에 맞춥니다. 원본 크기 프리셋은 기존처럼 `-fps_mode passthrough`로 시각을 그대로 씁니다.

기록 화면의 **MP4 GIF를 GIF로**(`HistoryWindow._convert_worker`)는 출처·작성자 기록과 같은 계정/출력 폴더 잠금을 잡고 한 파일씩 처리합니다. 임시 GIF에 출처·작성자를 기록하고 원본 수정 시각을 복사한 뒤 같은 이름의 `.gif`로 덮어쓰기 없이 옮깁니다. 이어 원본 MP4를 `SHFileOperationW`(`FOF_ALLOWUNDO`)로 휴지통에 보내고, 성공했을 때만 `replace_media_file`로 기록 경로를 바꿉니다. 휴지통으로 보내지 못하면 새 GIF를 지우고 MP4를 그대로 둡니다. `SHQueryRecycleBinW`가 실패하는 드라이브(네트워크 경로 등)는 변환하지 않습니다. 기록 갱신 전에 멈춰도 다음 새로고침의 파일 확인이 GIF 경로로 바로잡습니다.

`theme.apply(root, mode="light"|"dark")`는 같은 Tk 인터프리터의 기존·새 창을 함께 바꿉니다. 둥근 컨트롤 이미지는 재사용하고, `theme.Progressbar`는 실제 값과 시각 보간 값을 분리하므로 완료율을 만들어내지 않습니다. 테마 선택은 settings.json의 appearance에 보관하며 worker 옵션에는 보내지 않습니다. `theme.title_bar`는 창이 처음 표시될 때와 테마를 바꿀 때 `DwmSetWindowAttribute`(20, 이전 Windows 10은 19)로 제목 표시줄을 맞춥니다. 확인·안내 창은 `dialogs.py`의 테마 창으로, `tkinter.messagebox`와 같은 호출과 반환값을 씁니다. 파일·폴더 선택 창은 Windows 기본 창입니다.

Git에서는 Pretendard 글꼴(`*.ttf`)과 `tools/ffmpeg/runtime/ffmpeg.exe`를 Git LFS로 보관합니다(1.7.0부터, `.gitattributes`). 새로 받을 때는 Git for Windows에 포함된 Git LFS가 실제 파일을 받습니다. LFS 없이 받으면 작은 포인터 파일만 생기고 `build.py --check`와 글꼴 확인이 실패합니다. 이전 커밋의 파일은 기록에 그대로 남아 있습니다.

GIF 변환/동영상 섬네일에 쓰는 `tools/ffmpeg/runtime/ffmpeg.exe`는 필요한 로컬 코덱만 포함한 FFmpeg 7.1 빌드입니다. 실행 파일에 함께 들어가므로 사용자는 따로 설치할 필요가 없습니다. `tools/ffmpeg/build.py --check`로 바이너리·소스·빌드 설정의 SHA256을 확인합니다. 직접 다시 빌드하려면 `tools/ffmpeg/README.md`의 portable w64devkit 빌드 절차를 사용하세요. 배포 ZIP은 해당 버전의 원본 소스와 재현용 빌드 설정, 라이선스를 포함합니다.

## 1.11.1 검토 보완

외부 기록 사본을 합치는 중 잠금·읽기 오류가 나면 소비한 사본으로 표시하지 않습니다. 사본을 내보내기 직전에도 새 사본을 다시 확인하며, 합치지 못한 정상 사본은 덮어쓰지 않고 다음 실행에서 재시도합니다. 손상이 확인된 사본은 기존 정책대로 새 정상 사본으로 대체할 수 있습니다.

자동 기록 백업은 계정과 기록 DB 폴더 경로의 해시로 나눕니다. 같은 계정의 서로 다른 저장 폴더가 같은 날 백업해도 덮어쓰거나 복구 행을 섞지 않습니다. 과거 계정 단위 백업은 삭제하지 않으며, 출처 저장 폴더를 확정할 수 없으므로 자동 복구의 대체 자료로 섞지 않습니다. 복구 파서는 잘린 숫자를 0으로 만들지 않고 해당 셀을 건너뜁니다.

섬네일 모아보기는 UI 객체를 갖지 않는 단일 디코더를 사용하고 새 페이지가 대기 중인 옛 페이지를 대체합니다. 같은 페이지를 다시 표시할 때 이미 있는 타일·이미지를 재사용하되, 읽기 허용 경로와 파일 변경 여부는 매번 새로 확인합니다. 창을 닫으면 Tk 이미지와 콜백 참조는 UI 스레드에서 정리합니다.

기존 MP4 GIF 일괄 변환은 변환 전 원본의 크기·수정 시각·파일 식별값을 보관하고 최종 기록·휴지통 이동 전 다시 확인합니다. 다른 프로그램이 바꾼 MP4와 기록 복구에 실패한 GIF는 삭제하지 않습니다.

## 1.11.2 실제 파일 집계

`summary()`와 `statistics()`는 허용된 기록 경로의 현재 일반 파일을 확인하여 Windows 경로 대소문자를 정규화하고 같은 경로를 한 번만 집계합니다. 서로 다른 경로의 실제 복사본은 각각 집계합니다. 원본 media 행과 archive·likes·tweets는 변경하지 않습니다. `posts`·게시일 범위는 전체 이력, `current_posts`는 현재 파일의 트윗 수, `record_count`는 원본 행 수입니다.

`overview()`는 파일 수·유형·용량·메타데이터 개수·작성자 순위·저장월/게시월을 하나의 파일 스냅샷에서 계산합니다. 같은 파일의 최초로 알려진 saved_at을 사용하며 Like 발견월은 파일 존재 여부와 별개인 likes 이력입니다. GUI는 `overview(verify_files=False)`로 경로와 알려진 크기에서 빠르게 집계한 뒤 기존 백그라운드 `import_legacy(refresh=True)`로 실제 파일을 확인합니다. 페이지 이동은 전체 폴더를 다시 확인하지 않으며 새로고침에서 삭제·이동 결과를 반영합니다.

## 2.0.0 UI와 검증

메인 창은 사이드 메뉴와 스크롤 가능한 저장 대시보드로 나뉩니다. 좁은 창에서는 메뉴가 상단으로 이동합니다. 라이브러리는 파일·실행 기록·통계 탭을 사용하며 파일 관리 작업은 별도 창에서 시작합니다. `theme.py`는 라이트·다크 색상, 둥근 컨트롤, 선택 탭, 폰트와 여백을 공통으로 제공합니다. `ScrollableContent`는 실제 toplevel에 입력을 등록하되 가장 가까운 자기 콘텐츠만 처리합니다. Text·Treeview·자식 스크롤 뷰의 기본 입력을 유지하며 destroy 시 해당 바인딩과 타이머만 정리합니다.

저장 설정은 현재 화면 값을 미리 보여 주고, 취소 시 `_option_snapshot`으로 되돌립니다. 설정 저장은 기존 설정의 미디어·정리·확인 옵션만 합쳐 쓰므로 아직 적용하지 않은 계정·저장 폴더를 덮어쓰지 않습니다. 예약 등록은 로그인·용량·계정·폴더를 검증하고 기록 이전이 완료된 뒤 진행합니다. 예약 실행은 빠른 확인과 무제한 파일 수를 사용합니다. worker의 최종 상태와 종료 코드가 모두 성공일 때만 진행률을 완료로 표시합니다.

`tools/ui_qa.py`는 임시 앱 데이터, 예시 미디어와 기록을 만들어 화면을 캡처합니다. X 요청·로그인 저장·스케줄러 변경·다운로드를 막고 Tk 콜백 오류와 요청 시도를 검사합니다. 실제 계정 정보는 사용하지 않습니다. 기본 실행은 라이트·다크와 작은 창을 캡처하고 contact sheet와 manifest를 남깁니다. `--scaling 2 --output .test-output/ui2/large`로 큰 글꼴 배치도 확인할 수 있습니다. 전체 회귀 검사와 배포본 자체 점검 결과는 [2.0.0 검증 기록](review-2.0.0.md)에 정리합니다.

2.0.1부터 최초 창 크기와 기록 창의 실제 최대화 화면도 캡처합니다. `--screen-size 1366x768`은 QA fixture의 화면 크기만 모의하며 모니터 설정을 바꾸지 않습니다. [`2.0.1 검증 기록`](review-2.0.1.md)을 참고하세요.

## 2.1.0 사라진 파일

`HistoryStore._missing`은 미디어 식별자(트윗·번호·종류)마다 현재 파일이 하나도 없는 것을 모읍니다. 저장 방식이 달라 같은 미디어에 기록이 여럿이어도 한 번만 나오고, 한 기록이라도 파일이 있으면 사라진 것이 아닙니다. `summary()`의 `missing_files`도 이 기준이며 숨긴 것은 `ignored_missing`으로 따로 셉니다(기존 행 기준 값은 `unmatched_records`). `overview()`는 같은 스냅숏에서 전체 `missing` 목록을 함께 돌려줍니다. 2.1.1부터 5,000개 제한을 없애고 UI에서 숨김 필터 후 50·100·200개씩 표시합니다. 사라진 파일 페이지 이동은 이미 읽은 스냅숏을 사용하여 추가 DB·폴더 조회를 하지 않습니다.

`missing_choices(tweet_id, num, media_type, ignored, updated_at)`는 ‘다시 받지 않기’ 선택입니다. 숨김 해제도 행으로 남겨, 다른 PC 사본과 합칠 때(`storage._merge_history`) `updated_at`이 늦은 선택이 이깁니다. 기록 복구(`rebuild_history`)도 이 표를 살립니다. worker는 시작할 때 `ignored_media()`를 읽어 저장 방식과 관계없이 그 미디어를 건너뜁니다(중복 방지 기록이 없는 다른 방식의 archive에서도).

다시 받기는 `JobOptions.targets`(history.`archive_key` 형식, 최대 2,000개)로 실행합니다. worker는 Like 목록 대신 트윗마다 `https://x.com/i/web/status/<id>`를 `tweet-endpoint: restid`(TweetResultByRestId 1회)로 엽니다. 트윗을 처리하기 직전에 그 트윗의 고른 키만 현재 방식 archive에서 지우고(예전 `gif_` 표기·접두어 없는 표기 포함), 끝나면 받지 못한 항목의 원래 항목을 다시 넣습니다. 중단·요청 한도·오류에도 같습니다. 고르지 않은 같은 트윗의 다른 미디어는 건드리지 않고, 동영상·GIF 저장을 꺼 두었어도 고른 것은 받습니다(용량 제한은 적용). 실행은 `scan_mode='retry'`로 기록하고 `quick_scan_readiness`와 `LikeOrder`의 이전 완료 실행 판단에서 제외하며, Like 순서도 기록하지 않습니다. 트윗을 볼 수 없거나(디렉터리 메타데이터 없음) 미디어를 받지 못한 경우는 오류 대신 트윗 주소와 함께 안내하고 다음 트윗으로 넘어갑니다. 요청 한도·인증·저장소·기록 오류(`_FATAL_TERMS`)는 전체를 멈춥니다. 숨겼던 파일을 다시 받으면 숨김을 풉니다.

라이브러리 탭의 숨은 페이지는 마지막 너비를 유지하므로, 미리보기·통계 배치는 숨은 페이지일 때 노트북 너비(`_page_width`)로 정합니다. 좁은 창에서 쌓인 통계 페이지가 다른 탭을 길게 만들던 문제를 막습니다.

## 2.1.1 경계 조건 보완

라이브러리의 retry 콜백은 파일 키와 함께 표시 중인 계정·StoragePaths를 전달합니다. 메인은 현재 계정·기록 DB 경로·저장 경로를 먼저 비교하고, 달라졌으면 인증/기록을 변경하기 전에 새로고침을 안내합니다. 저장 방식과 계정별 하위 폴더 옵션은 현재 설정을 사용할 수 있습니다. 확인창 전의 선택 컨텍스트와 세대를 캡처하여, 확인창 중 새로고침·저장 시작·창 닫기가 발생하면 이전 선택을 적용하지 않습니다.

숨김 선택 worker는 `choice_active`로 메인 저장·기록 이전과 겹치지 않게 하며, AccountGuard와 OutputGuard로 다른 프로세스의 다운로드도 제외합니다. DB를 닫은 뒤 폴더 사본과 로컬 백업을 갱신하고 잠금을 해제한 다음 결과를 전달합니다. 사본/백업 실패는 로컬 선택을 보존하며 별도로 안내합니다. 창을 닫으면 선택 worker가 마칠 때까지 기다립니다. 일반 기록 로딩은 메인 저장을 막지 않습니다.

개별 재다운로드에서 gallery-dl의 정확한 `AuthRequired: Protected Tweet`·`AuthRequired: NSFW Tweet`만 트윗 접근 불가로 처리합니다. 다른 인증 로그·HTTP 401/403·요청 제한은 계속 전체 중단합니다. 복원 완료 항목의 숨김 해제는 worker의 `finally`에서 실행해 사용자 중단이나 후속 오류에서도 남깁니다.

테마 캐시는 필수 자산 명세와 ZIP 목록을 대조하고, 실제 Tk PNG 디코딩이 실패하면 모든 자산을 다시 생성해 한 번 교체합니다. 정상 캐시는 기존처럼 메모리/디스크에서 재사용합니다.

DB 초기화에서 제약 오류가 나면 그 오류 경로에서만 `quick_check`를 실행합니다. 실제 손상일 때는 `CatalogDamaged`로 분류해 기록 복구 버튼을 표시하며, 정상 DB의 제약 오류는 기존 일반 오류로 둡니다.

# 성능 개선 검증

2026-10-15, LuvBox 1.0.0 소스 수정. 개인 계정이나 실제 저장 폴더 대신 임시 DB와 생성한 이미지를 사용했습니다.

## 변경 사항

- **기록 조회:** 기본 저장 순서와 동일한 SQLite 인덱스, 대소문자를 구분하지 않는 작성자 인덱스, 이전 기록의 빈 출처 주소만 찾는 작은 인덱스를 추가했습니다. 파일 경로가 비어 있는지도 인덱스에 보관해 뒤쪽 페이지의 삭제 여부 확인을 빠르게 합니다. DB를 열 때마다 전체 기록에서 빈 출처를 찾는 작업을 줄입니다. 이전 DB의 열·기본 키 이전을 마친 뒤 인덱스를 만듭니다.
- **갤러리 선택:** 선택이 바뀐 타일만 다시 그립니다. 선택한 타일이 1,000개인 상태에서 선택을 그대로 동기화하면 1,000개 위젯을 다시 설정하던 작업이 없어집니다.
- **큰 갤러리:** 표시할 파일이 결과 큐의 240개 한도를 넘어도 현재 미리보기를 버리지 않고 화면 처리를 기다립니다. 새 페이지 요청과 창 닫기는 대기를 중단합니다. 요청 시작 시 최대 240개 캐시 항목의 참조를 잠시 보관해, 앞쪽 파일을 읽으며 뒤쪽 캐시를 밀어내는 반복을 줄입니다. 300개에서 400개로 늘리는 회귀 사례의 이미지 디코딩은 400회에서 160회로 줄었습니다.
- **사진 미리보기:** 원본 픽셀을 복사·회전하기 전에 표시 크기로 줄입니다. EXIF 회전에서 가로·세로가 바뀌는 경우 축소 경계도 맞바꿉니다. 갤러리와 저장 확인창에 적용하며 원본 파일은 수정하지 않습니다.

## 재현

프로젝트 루트에서 실행합니다. 벤치마크는 임시 폴더를 정리하고 JSON으로 결과를 출력합니다.

```powershell
.\.venv\Scripts\python.exe tools\benchmark_history.py --rows 100000 --repeats 7
.\.venv\Scripts\python.exe tools\benchmark_preview.py --repeats 7
```

기록 벤치마크는 같은 임시 DB에서 새 인덱스를 만들기 전후를 비교합니다. 사진 벤치마크는 6,000×4,000 PNG의 이전·현재 픽셀 처리 경로를 비교합니다. X 요청이나 실제 다운로드 속도를 측정하지 않습니다. 실행 중인 다른 작업과 디스크 캐시에 따라 시간은 달라집니다.

## 측정 결과

Windows, Python 3.12.14, SQLite 3.53.1, Pillow 12.3.0에서 워밍업 후 7회 중앙값입니다. 기록은 10만 건이며 페이지당 100개입니다.

| 작업 | 개선 전 | 개선 후 | 속도 배율 |
| --- | ---: | ---: | ---: |
| 기록창 첫 페이지 조회 | 128.4ms | 49.7ms | 2.6배 |
| 기록창 뒤쪽 페이지 조회(앞의 9만 건 건너뛰기) | 343.7ms | 62.7ms | 5.5배 |
| 기록창 작성자 필터 첫 페이지 조회 | 98.1ms | 13.3ms | 7.4배 |
| 기존 기록 DB 열기 | 32.8ms | 3.4ms | 9.7배 |
| PNG 픽셀 처리, 150×112 미리보기 | 67.5ms | 37.8ms | 1.8배 |
| PNG 픽셀 처리, 640×400 저장 확인창 | 74.4ms | 51.6ms | 1.4배 |

기록창 조회는 화면에서 사용하는 삭제 기록 제외 조건(`include_deleted=False`)을 적용했습니다. 파일 존재 재확인·전체 통계 계산·Tk 위젯 그리기를 포함한 창 전체의 표시 시간은 아닙니다. 원시 결과는 로컬 개발 산출물 `.test-output/performance-history-final.json`, `.test-output/performance-preview.json`에 보관합니다.

## 비용과 검증 범위

10만 건의 샘플 DB에서 인덱스는 약 7.9MiB(14.4%)를 추가하며 처음 열 때 한 번 생성합니다. 생성은 약 356ms, 1,000개 기록 일괄 추가는 11.8ms에서 19.8ms로 늘었습니다. 기본 저장 순서·작성자·이전 기록 확인에 필요한 세 인덱스만 사용합니다. 선택 가능한 게시일 정렬에도 인덱스를 추가하는 구성은 대량 입력 비용이 커서 제외했습니다.

회귀 검사는 기록의 기존 정렬·필터·이전 DB 호환성·손상 시 복구 안내, 파일 경로 허용 검사, 캐시 무효화, 갤러리 큐 포화·중단·선택 표시, EXIF의 여덟 방향과 투명 이미지·원본 보존을 확인합니다.

최종 전체 회귀 검사는 **1,002개 중 998개 통과, 4개 생략**입니다. `entry.py --self-test`의 소스 앱 자체 점검도 통과했습니다. 읽기 오류에서만 손상 여부를 확인하고, 손상된 행의 디코딩이 실패해도 커서를 정리해 복구를 막는 파일 잠금이 남지 않도록 검증했습니다. 결과는 `.test-output/performance-full-tests-final.log`, `.test-output/performance-source-selftest.json`에 있습니다.

후속 구조 정리와 최신 전체 검사·화면 검수 결과는 [리팩토링 검수](refactoring-review.md)에 있습니다.

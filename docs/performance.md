# 성능 구조와 재현

## 1.6.6 중복 검사 측정

Windows CPython 3.12.16·Pillow 13.0.0에서 생성한 4,000×3,000 RGB JPEG(EXIF 방향 6)를 각 구현마다 새 프로세스 5개에서 읽었습니다. 1.6.5와 1.6.6의 SHA-256과 dHash가 같음을 확인했습니다.

| 지표(5회 중앙값) | 1.6.5 | 1.6.6 |
| --- | ---: | ---: |
| 프로세스 최대 작업 집합 | 134,909,952바이트 | 98,877,440바이트 |
| 파일 해시·dHash 계산 | 161.2ms | 139.1ms |

흑백 변환 후 방향을 보정해 큰 RGB 복사본을 만들지 않습니다. 이 합성 표본에서 프로세스 최대 작업 집합은 약 26.7%, 처리 시간은 약 13.7% 줄었습니다. 회귀 테스트와 함께 측정한 로컬 값이며 이미지 형식·크기·캐시·PC에 따라 달라집니다. 앱 전체의 메모리나 모든 작업의 속도 개선율은 아닙니다.

중복 묶음 저장은 실패 시 전체 롤백을 위해 단일 트랜잭션을 사용합니다. 합성 해시 100,000개·묶음 50,000개를 5회 갱신한 중앙값은 1.115초(0.783–1.434초)였습니다. 사진 읽기·해시 비교는 이 쓰기 트랜잭션 밖에서 수행합니다. 훨씬 큰 카탈로그나 느린 디스크에서는 쓰기 대기가 길어질 수 있습니다. 로그는 `.test-output/review-166-benchmark.json`, `review-166-cluster-benchmark.json`에 보관합니다.

현재 앱은 PySide6 + Qt Quick을 사용합니다. 과거 Tk 화면의 콜백 빈도·스크롤 지연·CPU 측정값은 현재 UI의 성능 수치로 사용하지 않습니다. 이전 측정 원문은 [1.2.0 소스 기록](https://github.com/white-critter/LuvBox/blob/v1.2.0/docs/performance.md)에 보존합니다.

## 현재 경로

- 갤러리는 가시 항목을 우선 디코딩하고 제한된 lookahead·작업자·이미지 캐시를 사용합니다. 새 검색·정렬·초기화·종료 뒤 완료되는 오래된 작업은 세대로 구분해 버립니다. 파일·DB 읽기는 UI 밖에서 수행합니다.
- 큰 사진은 복사·회전 전에 표시 크기로 축소합니다. 원본 배율은 확인한 정지 사진과 픽셀 상한에 한정하며 GIF·영상은 화면 맞춤·확대를 사용합니다. 원본 미디어는 변경하지 않습니다.
- 래스터의 압축 입력도 64MiB 상한으로 읽습니다. WebP의 컨테이너 전체 읽기가 픽셀 확인 전에 큰 메모리를 할당하는 상황을 제한하며, 검사 뒤 파일이 커져도 같은 상한을 유지합니다.
- 저장 상세는 펼친 동안에만 정지 미리보기를 만듭니다. 현재 디코딩 한 개와 가장 최근 대기 요청 한 개만 유지합니다. GIF·동영상은 첫 프레임을 사용하며 진행률만 바뀔 때 큰 이미지 맵을 다시 전달하지 않습니다.
- worker 진행 알림은 소비자가 느려도 같은 전송의 최신 값으로 합칩니다. 저장·확인·완료·오류 이벤트를 버리거나 순서를 바꾸지 않습니다.
- 저장 폴더를 다시 읽을 때는 이미 불러 둔 기록에서 파일을 찾습니다. 파일마다 기록을 다시 조회하지 않습니다. 비어 있는 원문 링크는 한 번에 고치지 않고 500건씩 커밋합니다.
- 손상된 기록의 페이지 복구는 필요한 페이지만 읽습니다. 파일 전체를 메모리에 복사하지 않습니다.
- 기록 조회는 정렬·작성자·빈 출처에 필요한 SQLite 인덱스를 사용합니다. 좋아요 순서 배치는 한 번에 정렬하고 정렬 키 간격이 소진될 때만 재조정합니다. 인덱스는 디스크와 쓰기 비용을 추가하므로 선택적 정렬마다 무조건 늘리지 않습니다.
- 폴더형 EXE는 앱 실행과 저장 worker 시작마다 전체 Qt 런타임을 임시 폴더로 다시 풀지 않습니다. Qt에서 사용하지 않는 구성요소와 이전 UI 런타임은 수집하지 않습니다.

- 실행 기록은 작은 실행 기록부와 현재 계정 카탈로그의 실행 표만 50건씩 읽습니다. 예전 관리 화면처럼 카탈로그 전체 사본을 만들거나 모든 파일의 존재를 확인하지 않아 설정 창에서 바로 열립니다. 저장 못 한 미디어 목록도 최대 500건의 작은 기록부를 50건씩 읽습니다.

## 재현

프로젝트 루트에서 임시 DB·생성 미디어로 실행합니다. 개인 계정·실제 저장 폴더·X 요청을 사용하지 않습니다.

```powershell
.\.venv\Scripts\python.exe tools\benchmark_history.py --rows 100000 --repeats 7
.\.venv\Scripts\python.exe tools\benchmark_preview.py --repeats 7
.\.venv\Scripts\python.exe tools\qt_gallery_preview.py --rows 1000 --benchmark --output '.test-output\qt-gallery-benchmark.json'
```

기록 도구는 인덱스 전후 조회를, 사진 도구는 6,000×4,000 생성 PNG의 픽셀 처리만 비교합니다. Qt 도구는 격리된 갤러리 실험이며 전체 제품의 실제 라이브러리 부하와 동일하지 않습니다. `--help`로 스크롤·휠·배율 조건을 지정할 수 있습니다. 출력 경로를 사용할 때는 먼저 `.test-output`을 만듭니다.

측정은 테스트·빌드·다른 벤치마크와 겹치지 않게 실행합니다. OS·Python·Pillow·Qt 버전, 데이터 건수·미디어 크기, 배율·창 크기, 반복 수와 중앙값·범위를 함께 기록합니다. 파일 시스템 캐시와 백그라운드 작업에 따라 결과가 달라집니다. 이미지 처리 시간·UI 콜백 빈도·물리 화면 FPS·X 다운로드 대역폭을 구분합니다.

## 회귀와 해석

자동 테스트는 기존 정렬·필터·DB 이전, 캐시 상한·무효화·오래된 결과 배제, EXIF 회전·원본 보존, 미디어 파일 해제, 최신 진행 이벤트 유지와 불필요한 미리보기 재발행 방지를 확인합니다. 최신 전체 검사·빌드 결과는 [검증 기록](verification.md)을 따릅니다. 특정 합성 벤치마크의 개선을 전체 앱의 동일한 속도 향상으로 설명하지 않습니다. 장기 실행 메모리 증가와 사용자 라이브러리 규모의 체감 성능은 별도 관찰이 필요합니다.

## 2026-11-10 비둘기집 원리 기반 유사 해시 클러스터링과 단일 패스 해시

`cluster_duplicates`는 해밍 거리 `d <= 7`에서 64비트 dHash를 `d + 1`개의 서로소 비트 조각으로 나누어 같은 조각 값을 공유하는 후보끼리만 비교합니다(비둘기집 원리에 의해 해밍 거리 `d` 이하인 두 해시는 반드시 최소 1개 조각이 일치함). Windows, CPython 3.12.16에서 합성 고유 해시 20,000개와 근접 사본 50개(총 20,050개, 거리 4)를 클러스터링하는 시간은 약 67.8ms였으며, 전체 짝 비교 결과와 동일한 묶음을 만듭니다. 또한 `compute_image_hashes`는 한 번의 파일 열기와 스트림 되감기(`seek(0)`)로 SHA-256과 dHash를 함께 계산해 파일 열기 비용을 줄입니다.

## 2026-11-10 AI 특징값과 갤러리 즐겨찾기

Windows, CPython 3.12.16, SQLite 3.53.1에서 임시 카탈로그만 사용했습니다. 시간은 한 번 데운 뒤 5회 중앙값입니다. 이미지 파일과 ONNX 세션은 만들지 않았습니다.

배운 예제가 없을 때 자동분류는 특징값 BLOB을 읽지 않습니다. 4,000개의 512차원 특징값을 파이썬 딕셔너리로 읽는 조회는 25.34ms(범위 22.43–28.40ms)였고, 태그와 가르침만 읽는 조회는 0.016ms(0.016–0.021ms)였습니다. 예제가 있으면 그 예제의 특징값만 읽고, 이웃 비교는 분류마다 한 번의 행렬 곱으로 처리합니다. 4,000장과 가르친 분류 2개를 한 장씩 최대 유사도만 계산하면 25.48ms(24.90–26.42ms), 같은 입력을 일괄 비교하면 3.34ms(2.99–3.88ms)였습니다. 이 차이는 비교 루프이며 사진 디코딩이나 전체 자동분류 시간이 아닙니다.

갤러리 한 페이지는 즐겨찾기 표 전체를 만들지 않고 그 페이지의 항목만 조회합니다. 즐겨찾기 4,000개 전체를 읽는 데 4.72ms(4.31–4.92ms), 그중 80개만 조회하는 데 0.194ms(0.189–0.212ms)였습니다. 페이지를 그리는 시간은 포함하지 않았습니다.

## 2026-11-10 사본 선택과 저장된 중복 묶음

사본 일괄 선택은 검사 때 저장한 `cluster_id`만 읽습니다. 갤러리 화면에서 64비트 해시를 다시 짝지어 비교하지 않습니다. Windows, CPython 3.12에서 합성 해시 4,000개를 5회 측정했습니다. 이미지 파일은 만들지 않았고, 시간은 선택 단계만 포함합니다.

| 처리 | 조건 | 중앙값 | 범위 |
| --- | --- | --- | --- |
| `cluster_duplicates` 재비교 | 해시 4,000개, 거리 4 | 861.81ms | 830.95–881.22ms |
| 저장된 묶음에서 사본 읽기 | 묶음 400개(항목 800)와 나머지 3,200개 | 2.12ms | 1.95–2.46ms |

재비교 입력의 연속된 해시 값은 거리 4 안에서 한 성분으로 이어졌습니다. 이 표의 차이는 그 성분의 개수가 아니라 짝 비교를 하지 않는 데 있습니다. 같은 비율로 해시가 20,000개이면 재비교는 대략 20초 안팎이 되지만, 그 크기는 이번에 측정하지 않았습니다. 중복 필터는 묶음 번호가 있는 행에서 같은 해시 조회를 건너뛰며, 번호가 없는 예전 기록은 이전과 같이 같은 파일 해시를 찾습니다.

## 2026-11-05 갤러리 스크롤과 GIF 미리보기

갤러리의 다음 페이지는 라이브러리 컨트롤러의 공통 변경 신호로 알려졌고, 작성자 콤보가 그 신호를 작성자 목록이 바뀐 것으로 받아 목록 전체를 다시 만들었습니다. 작성자 목록과 선택된 작성자는 그 값이 바뀔 때만 별도 신호로 알립니다. 페이지를 더 읽는 동안에는 콤보를 다시 만들지 않습니다.

여러 장 선택도 같은 방식으로 나눴습니다. 보이는 칸은 선택 목록 전체를 복사해 찾지 않고, 선택 세대 번호와 그 칸의 키만 확인합니다. 휴지통으로 보낼 때는 이전과 같이 선택된 키 목록을 한 번 복사합니다.

저장하지 못한 미디어의 개수 갱신과 목록 페이지도 신호를 나눴습니다. 개수만 바뀌면 이미 만들어 둔 페이지와 그 미리보기 이미지를 다시 디코딩하지 않습니다.

GIF 미리보기는 논리 화면의 긴 변이 2,048px를 넘을 때만 그 변을 2,048px로 줄여 요청합니다. 화면 크기는 헤더 10바이트로 확인하고, 작은 GIF의 디코딩 크기는 바꾸지 않습니다. 이 상한의 메모리 차이를 대용량 GIF로 측정하지는 않았습니다.

## 2026-11-05 기록 화면·손상된 썸네일 읽기

여러 페이지의 저장 못 한 미디어에서 다시 저장 가능한 전체 개수를 QML 속성 getter가 직접 읽던 경로를 기존 기록 작업 스레드로 옮겼습니다. 화면 속성은 메모리의 값만 반환하며 목록 갱신·크기 제한 변경 때 다시 조회합니다. 이전 요청의 오류와 늦게 도착한 이전 크기 제한의 결과는 새 목록에 적용하지 않습니다.

Windows, CPython 3.12.16에서 임시 캐시의 8MiB BLOB과 정수 8,388,608을 각각 5회 읽었습니다. 수정 전 `Cache.get`은 현재 작업 시작 시점의 Git HEAD에서 가져왔습니다. Python 할당 피크 중앙값은 BLOB 8,388,887바이트·정수 8,388,785바이트에서 둘 다 1,384바이트로 줄었습니다. BLOB 조회 시간 중앙값은 11.808ms에서 0.010ms였습니다. 이는 손상된 캐시의 입력 방어 측정이며 정상 이미지 전체나 SQLite 네이티브 메모리의 개선율이 아닙니다. 재현 스크립트와 결과는 `.test-output/benchmark_cache_guard.py`, `cache-benchmark.json`입니다.

합성 미디어 1,000개의 Qt 갤러리 왕복 스크롤에서는 첫 화면 준비 528.498ms, UI 10ms 타이머 간격 p95 12.696ms·최대 29.994ms, 프로세스 작업 집합 최대 248,705,024바이트였습니다. 종료 후 썸네일 캐시·등록 경로·대기열·처리 중 작업은 모두 0이었고 작업 스레드 종료와 파일 잠금 해제를 확인했습니다. 실제 X 다운로드나 사용자의 전체 라이브러리·장기 실행 측정은 아닙니다. 원시 결과는 `.test-output/gallery-benchmark.json`입니다.

## 2026-10-30 썸네일 캐시 정리

Windows의 임시 SQLite 캐시 50,000행에서 같은 5,001행을 제거하는 1회 합성 측정입니다. 전체 `(rowid, size)` 목록 대신 삭제할 오래된 rowid만 압축 배열로 보관해 Python 할당 피크가 4,852,208바이트에서 52,404바이트로 줄었습니다. 시간은 0.133초에서 0.034초였으며 전체 앱 속도나 SQLite 네이티브 메모리 측정은 아닙니다. 삭제 순서와 크기가 다른 항목의 유지 결과는 회귀 검사로 확인합니다.

원시 결과와 재현 스크립트는 `.test-output/core-review/cache-prune-benchmark.json`, `benchmark_prune.py`에 보존합니다. 갤러리 파일의 일시적 잠금은 백그라운드에서 0.1·0.2·0.4초만 기다리며, 화면 밖 이동·목록 교체·종료 시 재시도를 취소합니다.

| 기록 사본의 게시물 병합 중 Python 신규 할당 피크 | 빈 대상 DB에 본문 약 1KB인 게시물 20,000개, 3회 중앙값 | 28,465,581바이트 | 32,292바이트 |
| 계정 상태 갱신의 파일 읽기·DPAPI 해독 | 계정 목록·활성 계정·연결 여부 한 번 갱신 | 3회 | 1회 |
| 예약 처리 중인 느린 썸네일과 같은 크기의 QML 요청 | 디코딩이 1초를 넘는 같은 파일 | 중복 디코딩 2회 | 공유 디코딩 1회 |

메타데이터는 반복 `list.count()`를 `Counter` 비교로 바꿔 중복값 보존 조건을 유지합니다. 10,000개 검증의 7회 범위는 변경 전 1.862~1.894초, 변경 후 2.417~5.216ms입니다. 이 수치는 목록 검증만 측정하며 ExifTool 실행·파일 복사·전체 저장 시간은 포함하지 않습니다.

기록 병합은 입력 행을 한 번에 목록으로 만들지 않고 SQLite cursor에서 순차 처리합니다. 매 반복마다 병합 후 모든 게시물 행이 원본과 같은지 확인했습니다. Python 할당 피크는 `tracemalloc` 측정값이며 SQLite 네이티브 메모리·OS 캐시·기존 대상 기록의 메모리를 나타내지 않습니다. 병합 시간 중앙값은 0.418초에서 0.393초였고, 개선 근거는 중간 입력 목록의 메모리 감소에 한정합니다.

측정 스크립트와 원시 결과는 검증 작업의 `.test-output/full-review/benchmark_metadata_verification.py`, `metadata-verification-benchmark.json` 및 `.test-output/storage-review/benchmark_merge_memory.py`, `merge-benchmark.json`에 보존했습니다. 계정 읽기 횟수·중복 디코딩은 회귀 검사에서 검증하며 Windows DPAPI 자체의 실행 시간을 측정한 것은 아닙니다.


## 2026-11-01 실행 기록과 저장 못 한 미디어 조회

Windows 11, Python 3.12.16, SQLite 3.53.1에서 임시 폴더의 생성 데이터만 사용했습니다. 시간은 한 번 데운 뒤 7회 중앙값입니다. 창을 그리는 시간은 포함하지 않습니다.

직접 제외 한 페이지는 제외 400건마다 미디어 2만 건을 조건 없이 다시 읽었습니다. 미디어 기본 키가 폴더 배치로 시작하는데 조회가 그 열을 빼서, 목록을 열 때마다 카탈로그 전체를 훑었습니다. 개수를 세는 경로도 같은 조회를 썼고, 실행 기록과 한 작업 스레드를 나눠 쓰므로 실행 기록 창도 그 조회가 끝날 때까지 기다렸습니다.

| 처리 | 조건 | 변경 전 | 변경 후 |
| --- | --- | --- | --- |
| 직접 제외 첫 페이지 | 미디어 20,000, 제외 400, 50건 | 6,450.8ms | 0.984ms |
| 제외 개수 | 같은 카탈로그 | 전체 페이지 조회와 같음 | 0.017ms |
| 실행 기록 첫 페이지 | 기록부 1,000건과 카탈로그 실행 | 8.26ms | 9.46ms |
| 저장 못 한 미디어 첫 페이지 | 실패·용량 500건 중 50건 | 4.09ms | 5.67ms |
| 로컬 미리보기 50장 | 이미 저장된 WebP를 PNG 데이터로 | — | 8.89ms |
| 미리보기 없음 50건 | 캐시는 있고 그림은 없음 | — | 2.05ms |

실행 기록과 실패 목록은 기록 상한 안에서는 10밀리초 안쪽이라 조회 방식과 캐시를 바꾸지 않았습니다. 차이는 측정 오차입니다. 미리보기는 페이지를 만드는 작업 스레드에서만 읽고, 캐시 파일이 없으면 0.2밀리초입니다. 제외 페이지의 변경 전후 범위는 6,350–6,669ms와 0.976–1.080ms입니다.

## 2026-11-01 배포 크기와 시작 측정

Windows 11 한 대에서 1.4.1과 1.4.0 실행 폴더를 번갈아 5회씩 측정한 값입니다(1.4.1은 두 번 측정해 10회). 앱 데이터는 임시 폴더로 격리하고 EXE를 직접 실행해, 프로세스의 보이는 최상위 창(제목이 ‘LuvBox’로 시작)이 나타날 때까지의 시간과 그 5초 뒤의 작업 집합·전용 메모리를 기록했습니다. 파일 캐시가 데워진 상태이며 첫 실행(캐시 없음)은 더 오래 걸립니다(이전 측정에서 1.4.0이 한 번 4.5초). 크기의 MiB는 1,024² 바이트입니다.

| 항목 | 1.4.0 | 1.4.1 |
| --- | --- | --- |
| 실행 폴더 | 216.7MiB (2,662개 파일) | 192.8MiB (2,319개 파일) |
| 배포 ZIP | 249.3MiB | 239.7MiB |
| 창 표시까지(중앙값) | 1.462초 | 1.451초 |
| 5초 뒤 작업 집합(중앙값) | 224.1MiB | 224.6MiB |
| 5초 뒤 전용 메모리(중앙값) | 212.2MiB | 211.8MiB |

줄어든 파일(Qt 번역, ExifTool HTML 설명서, Pillow AVIF)은 원래 열리지 않았으므로 시작 시간과 메모리는 같고, 효과는 디스크와 내려받기 용량에만 있습니다. 시작 시간·메모리의 차이는 측정 오차 범위입니다. ZIP의 절반 이상(135.2MiB)은 라이선스 준수를 위한 Qt 원본 소스라 줄일 수 없습니다.

참고로 미리보기 창의 영상 재생 객체(`MediaPlayer`·`AudioOutput`)는 앱이 시작될 때 만들어집니다. 이를 모두 빼 본 상한 실험(1.4.0 복사본에서 구성요소를 빈 껍데기로 교체)에서는 전용 메모리가 212MiB에서 188MiB로 줄었지만 작업 집합은 226MiB에서 219MiB, 창 표시는 1.69초에서 1.60초로 차이가 작았습니다. 실제로 지연 생성하려면 미리보기 구성요소를 참조하는 곳을 모두 바꿔야 해 회귀 위험이 이득보다 크다고 보아 적용하지 않았습니다.

미리보기 전환의 자원 점검은 합성 영상·GIF·사진 408회 전환과 150번의 열고 닫기에서 핸들·QML 객체·플레이어 수가 늘지 않는지 확인했습니다. 결과는 [검증 기록](verification.md)에 있습니다.

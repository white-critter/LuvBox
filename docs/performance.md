# 성능 개선 검증

2026-10-15, LuvBox 1.0.0 소스 수정. 개인 계정이나 실제 저장 폴더 대신 임시 DB와 생성한 이미지를 사용했습니다.

## 변경 사항

- **기록 조회:** 기본 저장 순서와 동일한 SQLite 인덱스, 대소문자를 구분하지 않는 작성자 인덱스, 이전 기록의 빈 출처 주소만 찾는 작은 인덱스를 추가했습니다. 파일 경로가 비어 있는지도 인덱스에 보관해 뒤쪽 페이지의 삭제 여부 확인을 빠르게 합니다. DB를 열 때마다 전체 기록에서 빈 출처를 찾는 작업을 줄입니다. 이전 DB의 열·기본 키 이전을 마친 뒤 인덱스를 만듭니다.
- **갤러리 선택:** 선택이 바뀐 타일만 다시 그립니다. 선택한 타일이 1,000개인 상태에서 선택을 그대로 동기화하면 1,000개 위젯을 다시 설정하던 작업이 없어집니다.
- **큰 갤러리:** 표시할 파일이 결과 큐의 240개 한도를 넘어도 현재 미리보기를 버리지 않고 화면 처리를 기다립니다. 새 페이지 요청과 창 닫기는 대기를 중단합니다. 요청 시작 시 최대 240개 캐시 항목의 참조를 잠시 보관해, 앞쪽 파일을 읽으며 뒤쪽 캐시를 밀어내는 반복을 줄입니다. 300개에서 400개로 늘리는 회귀 사례의 이미지 디코딩은 400회에서 160회로 줄었습니다.
- **사진 미리보기:** 원본 픽셀을 복사·회전하기 전에 표시 크기로 줄입니다. EXIF 회전에서 가로·세로가 바뀌는 경우 축소 경계도 맞바꿉니다. 갤러리와 저장 확인창에 적용하며 원본 파일은 수정하지 않습니다.

## 재현

프로젝트 루트에서 실행합니다. 벤치마크는 임시 폴더를 정리하고 JSON으로 결과를 출력합니다.

```powershell
.\.venv\Scripts\python.exe tools\benchmark_history.py --rows 100000 --repeats 7
.\.venv\Scripts\python.exe tools\benchmark_preview.py --repeats 7
```

기록 벤치마크는 같은 임시 DB에서 새 인덱스를 만들기 전후를 비교합니다. 사진 벤치마크는 6,000×4,000 PNG의 이전·현재 픽셀 처리 경로를 비교합니다. X 요청이나 실제 다운로드 속도를 측정하지 않습니다. 실행 중인 다른 작업과 디스크 캐시에 따라 시간은 달라집니다.

## 측정 결과

Windows, Python 3.12.14, SQLite 3.53.1, Pillow 12.3.0에서 워밍업 후 7회 중앙값입니다. 기록은 10만 건이며 페이지당 100개입니다.

| 작업 | 개선 전 | 개선 후 | 속도 배율 |
| --- | ---: | ---: | ---: |
| 기록창 첫 페이지 조회 | 128.4ms | 49.7ms | 2.6배 |
| 기록창 뒤쪽 페이지 조회(앞의 9만 건 건너뛰기) | 343.7ms | 62.7ms | 5.5배 |
| 기록창 작성자 필터 첫 페이지 조회 | 98.1ms | 13.3ms | 7.4배 |
| 기존 기록 DB 열기 | 32.8ms | 3.4ms | 9.7배 |
| PNG 픽셀 처리, 150×112 미리보기 | 67.5ms | 37.8ms | 1.8배 |
| PNG 픽셀 처리, 640×400 저장 확인창 | 74.4ms | 51.6ms | 1.4배 |

기록창 조회는 화면에서 사용하는 삭제 기록 제외 조건(`include_deleted=False`)을 적용했습니다. 파일 존재 재확인·전체 통계 계산·Tk 위젯 그리기를 포함한 창 전체의 표시 시간은 아닙니다. 원시 결과는 로컬 개발 산출물 `.test-output/performance-history-final.json`, `.test-output/performance-preview.json`에 보관합니다.

## 비용과 검증 범위

10만 건의 샘플 DB에서 인덱스는 약 7.9MiB(14.4%)를 추가하며 처음 열 때 한 번 생성합니다. 생성은 약 356ms, 1,000개 기록 일괄 추가는 11.8ms에서 19.8ms로 늘었습니다. 기본 저장 순서·작성자·이전 기록 확인에 필요한 세 인덱스만 사용합니다. 선택 가능한 게시일 정렬에도 인덱스를 추가하는 구성은 대량 입력 비용이 커서 제외했습니다.

회귀 검사는 기록의 기존 정렬·필터·이전 DB 호환성·손상 시 복구 안내, 파일 경로 허용 검사, 캐시 무효화, 갤러리 큐 포화·중단·선택 표시, EXIF의 여덟 방향과 투명 이미지·원본 보존을 확인합니다.

최종 전체 회귀 검사는 **1,002개 중 998개 통과, 4개 생략**입니다. `entry.py --self-test`의 소스 앱 자체 점검도 통과했습니다. 읽기 오류에서만 손상 여부를 확인하고, 손상된 행의 디코딩이 실패해도 커서를 정리해 복구를 막는 파일 잠금이 남지 않도록 검증했습니다. 결과는 `.test-output/performance-full-tests-final.log`, `.test-output/performance-source-selftest.json`에 있습니다.

후속 구조 정리와 최신 전체 검사·화면 검수 결과는 리팩토링 검수 문서(Tk 화면 기준, 1.1.5에서 정리·Git 기록 보관)에 있습니다.

이번 변경과 검증은 소스 실행 기준입니다. 배포 EXE·ZIP은 다시 빌드하지 않았습니다.

## 2026-10-20 UI 응답성 개선

갤러리는 고정 폭 셀·중앙 정렬을 사용하고, 화면에 보이는 행과 주변 한 행씩만 실제 위젯으로 유지합니다. Configure 요청은 idle 단계에서 병합하며, 화면을 벗어난 위젯은 재사용합니다. 전체 논리 좌표와 스크롤 영역은 별도로 계산하고 네이티브 프레임의 크기도 가시 영역 근처로 제한합니다. 레이아웃 중 `update_idletasks()`를 호출하지 않습니다. 열 수가 바뀌어도 현재 첫 항목을 근처에 유지합니다.

Linux, Python 3.13.5, Tk 8.6.16, Xvfb 1920×1080·Xfwm4 환경에서 생성한 placeholder 타일로 1440→780→1440px 리사이즈를 요청한 결과입니다. 이미지 디코딩·파일 접근을 포함하지 않습니다.

| 타일 수 | 레이아웃 콜백 p95 이전 → 수정 후 | 메인 루프 heartbeat 최대 간격 이전 → 수정 후 |
| --- | ---: | ---: |
| 기본 페이지 100개 | 20.49 → 0.55ms | 38.35 → 15.83ms |
| 최대 페이지 200개 | 26.57 → 0.39ms | 44.70 → 17.71ms |
| 작성자 더 보기 1,000개 스트레스 | 192.72 → 0.25ms | 287.10 → 16.15ms |

콜백 재진입 깊이는 3에서 1로 줄었습니다. 가상화 직전 1,000개 항목의 최대 heartbeat 간격은 70.36ms였으며, 같은 placeholder 리사이즈 조건에서 16.15ms가 되었습니다. 수치는 콜백·이벤트 루프 측정이며 화면 출력 FPS가 아닙니다.

추가로 150×112의 불투명 합성 사진 한 장을 1,000개 항목이 재사용하도록 디코딩을 마친 뒤 리사이즈했습니다. 네이티브 타일은 최대 56개, heartbeat p95는 두 실행에서 13.26·11.50ms였고 최대 간격은 60.95·14.96ms였습니다. 첫 실행의 긴 간격도 보존합니다. Python 레이아웃 콜백 밖의 지연 원인은 이 계측만으로 특정하지 못하며, 모든 프레임이 16.7ms 안에 끝난다는 의미가 아닙니다. 서로 다른 원본의 디코딩·투명 여백 합성·연속 스크롤을 포함한 측정과도 구분해야 합니다.

회귀 검사에서는 10,000개 논리 항목에서도 실제 위젯 수가 가시 영역에 비례하고, 마지막 선택·화면 밖 Shift 기준점·양방향 자동 스크롤 드래그·위젯 재사용 시 콜백·권한 철회·숨겨진 탭의 첫 표시·큰 DPI를 유지하는지 확인합니다. 위 측정은 위젯 가상화 단계의 결과이며 당시 PIL 참조는 항목 수에 비례했습니다. 아래 후속 변경에서는 PIL 캐시도 제한했습니다. 현재 `tools/benchmark_gallery.py`는 첫 가시 영역이 준비되면 측정을 시작하므로, 전체 디코딩 완료를 기다렸던 이전 사진 두 실행과 구분해야 합니다. 이전 사진 측정과 placeholder 원시 결과는 `.test-output/resize-audit/`에 보관합니다.

진행바는 `start(interval)`을 반영하고 시간 기준으로 다음 프레임을 예약합니다. 같은 격리 환경의 최종 `start(12)` 콜백 빈도는 48.95→83.32Hz, 중앙 간격은 20.39→12.26ms였습니다. 실제 다운로드 진행값 입력은 기존처럼 보통 250ms 간격이며, 화면 보간 타이머와 별개입니다.

메인 이벤트 처리는 약 6ms를 목표로 나눠 실행하며, 연속 진행값을 병합하고 로그·집계를 일괄 반영합니다. 다른 종류의 이벤트 경계와 모든 로그는 보존합니다. 최종 합성 saved 100개 처리의 한 poll은 25.82→4.49ms, log 100개는 35.70→2.61ms였습니다. 개별 콜백을 강제로 중단하는 방식은 아니므로 모든 작업의 6ms 이내 종료를 보장하지 않습니다. 진행·로그에서 큰 기록 창 모듈을 처음 불러오던 경로도 경량 표시 모듈로 분리했고, 첫 progress 100개 poll은 1.23ms였습니다. 실행 부하에 따라 수치는 달라집니다.

로그인·설정 팝업과 메인 창은 숨긴 상태에서 구성한 뒤 표시합니다. 버튼·메뉴의 갑작스러운 위치 변경, 작은 확인창의 문구 잘림, 라이브러리 페이지 이동·파일 열기가 화면 밖으로 밀리던 배치도 보완했습니다. 관련 회귀 검사는 `tests/test_gui.py`, `test_ui_event_budget.py`, `test_gallery.py`, `test_gallery_virtual.py`, `test_history_gui.py`, `test_review_gui.py`, `test_theme.py`에 있습니다.

원시 계측·화면 검수 자료는 개발 산출물 `.test-output/resize-audit/`, `.test-output/ui-performance-audit/`, `.test-output/ui-ux-after/`, `.test-output/library-layout-after/`에 보관합니다. Windows 실제 렌더링과 EXE 재빌드는 별도 확인 대상이며, 이 Linux 수치로 검증 완료를 주장하지 않습니다.

## 첫 테마 적용의 이미지 생성 제거

밝음·어두움 테마의 105개 PNG를 `assets/theme/light.zip`, `dark.zip`으로 미리 생성합니다. 소스·설치판 모두 식별값이 맞는 번들을 읽으므로 첫 실행과 첫 어두운 테마 전환에서 Python 픽셀 루프를 실행하지 않습니다. 버전·팔레트·정확한 이미지 명세·렌더러 revision으로 식별값을 만들며, 누락·오래된 번들·잘못된 PNG는 기존 생성·설치판 캐시 경로로 복구합니다. `build.ps1`은 PyInstaller 전에 두 파일을 다시 생성하고 명시적으로 포함합니다.

동일 Linux·Tk·Xvfb 환경의 빈 Tk 창에서 7회 중앙값입니다. 두 경로 모두 메모리·설치판 디스크 캐시를 비운 조건이며, 이미지 생성 외의 PNG 디코딩·Tk 테마 적용 비용도 포함합니다.

| 작업 | 실행 중 생성 | 사전 생성 번들 |
| --- | ---: | ---: |
| 첫 밝은 테마 적용 | 453.98ms | 75.74ms |
| 밝음 이후 첫 어두운 테마 전환 | 434.78ms | 64.71ms |

PNG 생성 자체는 368.47ms, 번들 읽기는 1.99ms였습니다. 이후 메모리 캐시가 있는 전환도 Tk 이미지 갱신 비용이 남으며 밝음 63.10ms·어두움 56.72ms였습니다. 빈 창의 동기 적용 시간으로 실제 화면 출력 FPS나 위젯이 많은 창 전체의 전환 시간을 뜻하지 않습니다. 원시 결과와 재현 스크립트는 `.test-output/theme-bundle/`에 있습니다.


## 화면 주변 디코딩과 이미지 캐시 제한

전체 목록의 파일을 미리 읽고 PIL 이미지를 모두 보관하던 경로를 없앴습니다. 실제 보이는 행을 먼저 읽고 주변 한 행씩만 추가로 요청합니다. 스크롤로 요청 영역이 바뀌면 이전 요청을 취소하며, 새로고침 후에는 RAM 캐시도 해당 세대의 경로 권한과 파일 신원을 작업자에서 다시 확인합니다. 접근할 수 없는 원본의 보관 미리보기 복구는 유지합니다.

UI의 PIL 이미지는 LRU 240개를 기본 상한으로 사용합니다. 한 화면 자체가 240개를 넘으면 현재 마운트된 타일 수까지 허용하며, 전체 목록 크기와는 무관합니다. 디코더의 파일 신원 캐시 240개, 현재 배치의 보존 참조 최대 240개, 결과 큐 240개는 별도로 제한됩니다. 서로 같은 이미지 객체를 공유하므로 각 공간의 개수를 더한 값이 실제 이미지 수인 것은 아닙니다. 논리 항목·캡션·경로 등의 메타데이터는 여전히 목록 크기에 비례합니다.

결과 표시는 기록 창의 120ms poll만 기다리지 않고 갤러리 자체 8ms 타이머에서 처리합니다. 한 번에 최대 8개·약 3ms의 협력적 예산을 사용하며, 단일 Tk 호출을 중간에 중단하는 보장은 아닙니다. 타일마다 Tcl 이미지 버퍼 하나를 재사용합니다. 사진의 투명 픽셀과 여백은 선택 색상·현재 테마에 맞춰 Pillow에서 RGB로 합성해 Tk의 반복 투명 합성 비용을 줄였습니다. 원본 이미지·파일은 변경하지 않습니다.

서로 다른 PNG 1,000개(가로·세로·투명/반투명 영역)를 생성해, 첫 가시 영역이 준비되면 166회 리사이즈 후 목록을 120단계씩 왕복했습니다. UI 검사와 동시에 실행하지 않은 Linux/Tk/Xvfb 결과입니다.

| 항목 | 위젯 가상화만 적용 | 캐시 제한·지연 디코딩·RGB 합성 |
| --- | ---: | ---: |
| UI PIL 이미지 최대 | 1,000개 | 240개 |
| 관측 PIL 픽셀 버퍼 최대 | 45.76MB | 16.52MB |
| 첫 가시 영역 준비 | 333.34ms | 285.00ms |
| 첫 가시 영역까지 원본 디코딩 | 265회 | 56회 |
| 리사이즈 heartbeat p95 / 최대 | 16.27 / 27.85ms | 10.94 / 15.01ms |
| 왕복 스크롤 heartbeat p95 / 최대 | 17.90 / 30.91ms | 8.90 / 28.87ms |
| 스크롤 중 가시 항목 완료 상태 비율 평균 | 97.8% | 99.9% |

10,000개에서도 같은 항목 이동 속도가 되도록 방향당 1,200단계로 늘린 왕복은 58.69초였습니다. UI/디코더 캐시는 각각 240개, Tk 이미지·위젯은 72개, 관측 PIL 픽셀 버퍼는 최대 16.11MB였고 가시 항목 완료 상태 비율 평균은 99.2%였습니다. 스크롤 heartbeat p95는 9.45ms였지만 최대 126.33ms, poll 최대 55.33ms가 관측됐습니다. 9,216개 간격 중 30개가 16.7ms를 넘었습니다. 긴 지연을 제외하거나 원인을 확인하지 않고 프레임 지연이 없다고 해석하지 않습니다. 같은 10,000개를 단지 방향당 120단계로 이동한 별도 빠른 점프 스트레스에서는 준비율이 6.2%에 불과했으므로 사진 스크롤 성능의 근거로 사용하지 않습니다.

관측 버퍼는 UI 캐시·디코더 캐시·결과 큐의 객체를 중복 제거한 픽셀 수 추정입니다. 디코더 지역 보존 참조·진행 중 원본·Tk 저장 공간·Python 객체·프로세스 RSS를 포함하지 않습니다. 메모리를 제한해 퇴출한 항목은 다시 방문할 때 재디코딩할 수 있으며, 이 왕복에서 총 디코딩은 1,000→1,760회로 늘었습니다. RGB 합성 전의 캐시 제한만으로는 스크롤 p95가 약 20ms로 악화됐던 결과도 원시 자료에 보존합니다.

```powershell
.\.venv\Scripts\python.exe tools\benchmark_gallery.py --rows 1000 --unique --scroll
.\.venv\Scripts\python.exe tools\benchmark_gallery.py --rows 10000 --unique --scroll --scroll-steps 1200
```

위 긴 실행의 완료 비율은 해당 세대의 결과 도착을 기준으로 집계했으며, 생성된 PNG가 정상 디코딩됐다는 전제입니다. 현재 도구는 여기에 실제 Tk 사진 할당도 요구하고, 미리보기 실패와 대기를 따로 집계합니다. 16개 중 4개의 파일이 없는 짧은 검증에서는 사진 준비 12개·실패 4개로 구분했습니다. 현재 도구는 준비율·구간 시간·관측 오버헤드도 기록합니다. 이미지가 빈 상태에서 타이머만 빠른 결과를 사진 스크롤 성능으로 해석하지 않습니다. 첫 표시와 간헐적인 긴 간격은 남아 있으며 이 수치로 Windows 화면 FPS를 보장하지 않습니다. 원시 결과는 `.test-output/cache-audit/`에 보관합니다. 캐시·버퍼 재사용·투명 합성·테마/선택·권한·취소·자체 poll·종료 회귀 검사는 `tests/test_gallery_cache.py`에 있습니다.


선택적 `--trace-slow`는 느린 구간의 wall 시간·스레드/프로세스 CPU, 사진 버퍼 갱신, 작업자 디코딩, GC와 cgroup 제한을 기록합니다. 계측 오버헤드가 있는 진단 실행이므로 이전 비계측 수치와 직접 교체하지 않습니다.

10,000개 진단 재실행에서는 원래 126.33ms 지연이 재현되지 않았고, 스크롤 p95 9.12ms·최대 31.14ms였습니다. 최대 스크롤 간격 동안 UI 스레드 CPU는 0.18ms였고, 작업자의 한 디코딩과 겹쳤습니다(28.78ms 경과·27.61ms 작업자 CPU). 버퍼 `paste` 최대는 3.31ms였으며, 작업자 경합·스케줄링 대기와 양립하는 관측이지만 GIL 원인을 입증하지는 않습니다. 초기 표시의 66.19ms 간격은 UI CPU 60.12ms로 초기 구성 비용이 컸습니다.

이 진단에서 GC 최대는 1.70ms였고, cgroup CPU 제한 대기는 0회였습니다. 따라서 앞선 비계측 126ms를 GC나 클라우드 CPU 제한 탓으로 단정하지 않습니다. 원시 진단은 `.test-output/cache-audit/after-10000-unique-rgb-trace.json`에 있으며, 드문 긴 간격과 Windows 실제 표시 성능은 남은 검증 범위입니다.

## 2026-10-21 첫 갤러리 표시의 글꼴·디코더 준비 비용

캡션 폭을 재는 named font와 타일에 표시하는 tuple font가 서로 달랐습니다. 표시하는 위젯이 없는 측정용 글꼴은 새 문구를 잴 때 네이티브 글꼴을 반복해서 준비했습니다. 타일도 같은 named font를 사용하도록 바꾸고, 각 Label이 초기화 중 잠시 사용하는 `TkDefaultFont`는 숨긴 빈 Canvas 항목 하나로 유지합니다. 추가 위젯이나 표시 영역은 생기지 않으며 갤러리 해제 시 함께 정리합니다. 실행 중 Tk 배율이 바뀌면 named font의 포인트 크기를 다시 적용하고 캡션 캐시를 비워 실제 표시와 측정의 배율을 맞춥니다.

같은 Linux/Tk/Xvfb 환경에서 서로 다른 작성자·날짜 1,000개와 생성 PNG 한 장을 사용했습니다. 새 프로세스에서 이전 글꼴 연결 방식과 현재 방식만 교대로 바꾼 각 5회 중앙값입니다. 두 경로 모두 아래 디코더 개선을 사용했습니다. cProfile 계측이 포함되므로 일반 실행의 표시 시간과 직접 비교하지 않습니다.

| 작업 | 이전 글꼴 연결 | 글꼴 재사용 |
| --- | ---: | ---: |
| 캡션 폭 측정 113회 합계 | 111.74ms | 2.16ms |
| Label 생성 57회 합계 | 65.64ms | 5.27ms |
| 첫 `show()` 동기 처리 | 57.51ms | 10.54ms |

합성 150×112 PNG의 첫 `thumbnail()`만 새 인터프리터에서 교대로 7회 측정한 중앙값은 **25.86→7.18ms**였고, 불러온 이미지 플러그인 모듈은 **45→4개**였습니다. 등록에 걸린 시간도 새 수치에 포함됩니다. 따뜻한 캐시에서 반복 디코딩이 빨라졌다는 결과는 아니며, 앞선 10,000개 스크롤의 늦은 단일 디코딩 지연 원인을 입증하지도 않습니다. 원시 결과·재현 스크립트는 `.test-output/decode-contention-audit/cold-plugins-comparison.json`, `cold_plugins_compare.py`에 있습니다.

## 2026-10-21 같은 테마의 재표시와 저장 확인창 재생

Canvas의 `<Map>` 이벤트도 테마 재그리기를 요청합니다. 갤러리는 같은 테마로 탭을 다시 열 때도 placeholder를 새로 만들고 보이는 사진을 전부 재합성했습니다. 마지막으로 그린 테마를 보관해 같은 경우 생략합니다. 선택 변경은 해당 타일을 직접 갱신하고, 실제 밝음·어두움 변경은 기존처럼 모든 표시 사진의 투명 여백을 다시 합성합니다.

합성 PNG와 서로 다른 캡션 1,000개를 준비한 실제 Notebook에서 탭을 숨겼다가 다시 선택했습니다. 같은 Linux/Tk/Xvfb 환경에서 재표시 7회 중앙값은 **20.97→7.96ms**, 메인 스레드 CPU는 **15.73→4.97ms**였습니다. 재표시마다 실행되던 사진 48장의 재합성은 **48→0회**가 되었고 사진 버퍼·선택·placeholder를 유지했습니다. Tk 이벤트 처리를 포함한 재표시 비용으로 디스플레이 FPS는 아닙니다. 진단 스크립트와 원시 자료는 `.test-output/remaining-latency-audit/gallery_remap.py`, `gallery-remap-before.json`, `gallery-remap-after.json`에 있습니다.

저장 확인창은 고정 20ms poll이 각 프레임의 기한을 넘겨 다음 프레임을 표시했습니다. 같은 83ms 프레임도 렌더링 비용에 따라 약 84ms 또는 104ms 후에 표시돼 속도가 흔들렸습니다. 현재는 시간 기준 프레임 기한에 맞춰 예약하며, 큐 고갈이나 큰 UI 지연 뒤에는 새 기한으로 시작해 빠르게 따라잡는 점멸을 피합니다. 긴 GIF 프레임의 표시 시간은 유지하고, 디코더가 끝난 정지 사진은 불필요한 poll을 중단합니다.

같은 크기의 Tk 사진 버퍼를 재사용하고 투명 픽셀은 Canvas 배경에 맞춰 RGB로 합성합니다. 정지 사진도 테마 변경 시 원본 알파로 다시 합성하며, 원본 픽셀은 바꾸지 않습니다. 크기가 바뀌면 새 사진 버퍼를 만들고, 창 종료 시 예약 콜백·테마 콜백·사진 참조를 정리합니다.

항상 준비된 3프레임 제한 큐에 생성 RGB/RGBA 사진을 넣고, 각 조건에서 서로 다른 30프레임의 실제 표시 콜백을 측정했습니다. 창의 크기가 안정된 뒤 시작하고 같은 원본의 resize 재그리기는 프레임 수에서 제외합니다. 디코딩과 네트워크는 포함하지 않습니다.

| 조건 | 표시 콜백 빈도 이전 → 수정 후 | 프레임 렌더 중앙값 이전 → 수정 후 |
| --- | ---: | ---: |
| RGB, Canvas 680×449 | 10.92→12.06Hz | 2.18→1.18ms |
| RGB, Canvas 440×154 | 11.76→12.04Hz | 4.12→4.05ms |
| RGBA, Canvas 680×449 | 11.66→12.07Hz | 2.78→1.94ms |
| RGBA, Canvas 440×154 | 11.45→12.06Hz | 6.26→5.50ms |

일반 RGB의 프레임 간격 p95는 103.81→84.11ms였습니다. 각 조건의 Tk 사진 ID 생성은 30→1개로 줄었습니다. 작은 RGBA 조건의 heartbeat 최대는 14.67→11.15ms였습니다. **기존 미리보기 디코더의 12fps 상한은 유지**하며, 이 결과가 60fps 영상 재생이나 모든 프레임의 무지연을 의미하지 않습니다. 원시 결과는 `.test-output/remaining-latency-audit/review-before.json`, `review-after.json`, 재현 스크립트는 `benchmark_review.py`입니다.

갤러리 외의 저장 확인 사진·GIF·BMP 영상과 보관 JPEG/WEBP 읽기도 지원 플러그인 지연 등록을 사용하도록 맞췄습니다. 보관 미리보기의 import는 호출 시점에 수행해 `preview`와 `thumbcache`의 순환 import를 피합니다. 이 경로들의 첫 호출은 합성 파일을 만든 부모와 다른 새 인터프리터에서 전체 Pillow 초기화를 실패하도록 대체해 검사합니다. 기존 허용 형식·크기 제한·파일 신원 검사·취소 동작은 유지합니다.

## 작성자 검색의 협력적 목록 갱신

작성자 검색은 입력할 때마다 StringVar trace에서 기존 Treeview 전체를 지우고 통계의 작성자 목록을 동기 삽입했습니다. DB 조회는 이미 작업자에서 처리했지만 이 화면 갱신은 UI 스레드를 차단했습니다.

현재는 순위 키를 유지해 기존 행을 재사용하고, 약 3ms 또는 최대 512개 항목을 살핀 뒤 다음 이벤트 루프로 넘깁니다. 삭제도 한 번에 최대 512개로 묶습니다. 새 검색·통계는 이전 세대를 취소하고, 숨긴 탭은 다음 표시까지 갱신을 미룹니다. 작은 목록은 즉시 처리하되 큰 이전 목록을 정리해야 하는 경우는 분할합니다. 한 개의 Tk 호출을 중간에 중단하는 보장은 아닙니다.

갱신 도중에는 선택된 작성자의 신원과 샘플을 보관합니다. 새 순위가 적용되기 전의 행을 사용자가 선택해도 이미 처리된 새 순위까지 신원으로 찾아 복원합니다. 중간의 빈 선택 이벤트로 사진을 지우지 않으며, 최종 검색에서 제외된 작성자는 완료 시 정리합니다. 같은 검색의 새로고침은 스크롤을 보존하고, 검색어 변경은 위에서 시작합니다. 창 종료 시 타이머와 검색 trace를 해제합니다.

합성 작성자 10,000명의 실제 HistoryWindow/Treeview에서 각 동작을 한 번씩 실행했습니다. 생성자·테마 적용은 제외하며 DB·API·실제 미디어는 사용하지 않습니다. 측정 시작 시 목록이 비어 있는지 확인해 탭 표시 과정의 사전 채움이 섞이지 않도록 했습니다.

| 작업 | heartbeat 최대 이전 → 수정 후 | 완료 확인 이전 → 수정 후 |
| --- | ---: | ---: |
| 전체 10,000명 표시 | 79.12→6.69ms | 80.73→128.78ms |
| 100명 일치 검색 | 19.98→9.85ms | 20.03→60.54ms |
| 검색 3개 연속 입력, 마지막 10명 | 94.65→4.59ms | 108.17→34.36ms |

원시 자료는 `.test-output/remaining-latency-audit/authors-final-legacy.json`, `authors-final-batched512.json`, 재현 스크립트는 `benchmark_authors.py`입니다. `authors-before.json`, `authors-after.json`, `authors-cap*.json` 등은 초기 설정·분할 수 실험으로 최종 비교 근거에 사용하지 않습니다.

## 2026-10-22 저장 확인창 30Hz 재생과 남은 긴 지연

앞선 2026-10-21 측정 당시 유지했던 미리보기 디코더의 12fps 상한을 30fps로 높였습니다. GIF는 `1000/30`ms의 유리수 간격으로 샘플링해 반복 끝의 짧은 시간을 버리지 않으며, 영상 프레임의 표시 시간도 33ms 정수로 잘라 누적하지 않습니다. 긴 GIF 정지 구간은 하나의 프레임을 해당 시간 동안 유지합니다. 결과 큐가 가득 차면 작업자는 소비 알림을 기다리며, 50ms 대기는 화면이 멈춘 동안 watchdog을 갱신하기 위한 상한입니다. 매 프레임을 50ms 간격으로 공급하는 방식은 아닙니다.

Linux, Python 3.13.5, Tk 8.6.16, Xvfb·Xfwm4에서 실제 저장 확인창을 사용했습니다. 각 조건·이전/현재 경로를 새 프로세스에서 실행하고, 창 크기를 안정시킨 뒤 0.5초 준비·4초 측정했습니다. 합성 RGB 공급원 외의 세 조건은 실제 영상/GIF 디코딩을 포함합니다. 시험 파일 생성·테마 적용·창 구성은 측정 구간 밖입니다. 영상은 시험용으로 시스템 `/usr/bin/ffmpeg`를 주입했으며, 제품의 고정 Windows FFmpeg 경로는 바꾸지 않았습니다.

| 조건 | 표시 콜백 이전 → 현재 | Python CPU 이전 → 현재 | FFmpeg 자식 CPU 이전 → 현재 | 5ms heartbeat 최대 이전 → 현재 |
| --- | ---: | ---: | ---: | ---: |
| 항상 준비된 합성 RGB | 12.05 → 29.99Hz | 4.33 → 7.57% | 0 → 0% | 6.71 → 7.27ms |
| 1280×720, 30fps 영상 | 12.05 → 30.00Hz | 5.51 → 11.02% | 7.58 → 9.91% | 8.45 → 9.41ms |
| 160×100 GIF, 작은 창 | 12.05 → 30.00Hz | 15.73 → 8.44% | 0 → 0% | 13.40 → 7.63ms |
| 1280×800 투명 GIF | 12.05 → 29.99Hz | 65.62 → 103.02% | 0 → 0% | 7.38 → 8.41ms |

CPU 100%는 논리 CPU 하나의 사용량입니다. Python 수치는 UI와 디코더 작업자를 포함한 프로세스 전체이며, 영상의 FFmpeg 자식 사용량은 별도로 집계했습니다. 새 원본 프레임으로 실제 Tk 사진을 갱신한 콜백만 세고 resize 재그리기는 제외했습니다. 최종 프레임 간격 p95는 표 순서대로 34.29·35.71·34.14·34.43ms였습니다. 이 짧은 재생 구간에서 heartbeat가 16.7ms를 넘은 경우는 없었지만, Linux 콜백 Hz가 물리 디스플레이 FPS나 장시간 무지연 재생을 보장하지는 않습니다.

작은 GIF는 작업자에서 640×400으로 미리 확대했다가 실제 Canvas에 맞춰 다시 축소하던 비용을 제거했습니다. 원본 크기의 독립 RGBA 프레임을 전달해 원본 수명·투명도를 유지하며, 최종 표시 크기는 UI에서 정합니다. 30fps만 먼저 적용한 중간 실행은 Python CPU 38.72%·heartbeat 최대 30.30ms였고, 사전 확대 제거 후 작은 GIF 조건을 다시 측정한 결과가 표의 8.44%·7.63ms입니다. 최종 자료는 이 재측정과 영향을 받지 않은 나머지 세 조건의 앞선 30fps 실행을 합친 것이며, 네 조건을 모두 재실행했다고 해석하지 않습니다. 큰 투명 GIF는 약 30Hz를 공급했지만 Python CPU가 65.62→103.02%로 늘었습니다. 이 경로의 높은 디코딩·축소 비용은 남아 있어 저사양 PC에서도 같은 처리율이나 낮은 CPU 사용량을 보장하지 않습니다.

네 조건 모두 관측 큐 최대는 3개·재사용 Tk 사진 버퍼는 1개였습니다. 최종 Python RSS 표본 최대는 각각 63.84·67.61·56.75·81.04MiB였고, 영상의 FFmpeg 자식은 별도로 62.71MiB였습니다. RSS는 주기적 표본이므로 정확한 순간 최대나 전체 메모리 상한이 아니며, 두 프로세스의 공유 페이지는 겹칠 수 있습니다. 큐 3개 외에 디코딩 중 원본·작업자 지역 참조·현재 표시 프레임·Tk 저장 공간이 존재합니다. 닫기 UI 호출은 0.23~0.50ms, 닫은 뒤 결정 콜백까지는 25.95~26.63ms였습니다. 정리 확인 시 큐는 비어 있었고 작업자·watchdog·FFmpeg 자식은 모두 종료됐습니다. 닫기 호출에서 UI 스레드가 작업자 종료를 기다리지는 않습니다. 재생·유리수 타이밍·큐 소비 알림·포화 중 watchdog·취소·작은 RGBA 프레임 독립성의 집중 회귀 검사 25개가 통과했습니다. 원시 결과와 진단 스크립트는 `.test-output/playback-final-audit/`의 `playback-12fps.json`, `playback-30fps.json`, `playback-30fps-small-native.json`, `playback-30fps-final.json`, `playback-comparison.json`, `benchmark_playback.py`에 있습니다.

별도로 서로 다른 사진·캡션 10,000개를 왕복하며 heartbeat 경계의 Linux 스케줄러 카운터까지 추적했습니다. 사진 준비 비율 평균은 99.5%, 스크롤 heartbeat p95는 8.757ms였지만 최대 **66.535ms**가 남았습니다. 스크롤 9,277개 간격 중 15개가 16.7ms를 넘었습니다. 최대 구간의 UI 스레드 CPU는 3.683ms·프로세스 CPU는 4.082ms였고, 실행 가능 상태의 스케줄러 대기는 0.118ms였습니다. 따라서 그 구간 전체를 UI 연산이나 CPU 실행 순서 대기로 설명할 수 없습니다. 경과 시간에서 UI CPU를 뺀 62.852ms에는 타이머의 의도적 대기·차단 등도 포함되므로 특정 대기 원인의 측정값으로 취급하지 않습니다. 반대로 다른 47.294ms 구간은 UI CPU가 42.392ms였고, 초기 표시에서는 작업자 디코딩과 긴 간격이 겹쳤습니다. 서로 다른 긴 구간에 연산과 대기가 섞여 있으며, 겹침이나 문맥 전환 횟수만으로 GIL·디코더·OS 중 하나를 치명적인 단일 원인으로 입증하지 못했습니다.

이 추적의 GC 최대는 0.334ms, cgroup CPU quota 제한 대기는 0회였습니다. 사진 버퍼 `paste` 최대는 3.210ms였으며, 이 실행의 긴 구간 전체를 GC·quota·사진 복사 하나로 설명할 근거도 없습니다. 스케줄러 카운터는 개별 호출 내부가 아닌 heartbeat 경계에서 읽었습니다. 카운터 읽기만 총 963.562ms·한 번 최대 4.684ms의 오버헤드가 있었으므로, 이전 비계측 실행이나 스케줄러 표본이 없던 trace와 수치를 직접 교체하지 않습니다. 원시 추적과 요약은 `.test-output/gallery-final-audit/gallery-10000-scheduler.json`, `gallery-10000-scheduler-summary.json`에 보관합니다.

위 결과는 Linux 소스 실행의 측정입니다. Windows 실제 창 리사이즈·열기/닫기·진행바·재생의 화면 표시, 고정 Windows FFmpeg에서의 처리율·CPU·취소, 배포 EXE·ZIP 빌드 및 실행 검증은 남아 있습니다. 간헐적인 긴 간격과 큰 투명 GIF의 CPU 비용을 해결 완료로 기록하지 않습니다.

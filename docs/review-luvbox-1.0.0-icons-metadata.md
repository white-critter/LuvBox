# LuvBox 1.0.0 아이콘·출처 기록 검토

2026-10-14. Claude의 2f0e13b 변경을 바탕으로 사용자 요청을 처리했다. 버전과 기존 v1.0.0 태그를 유지한다.

- 작업표시줄 그룹의 재실행 명령·하트 ICO·표시 이름·명시적 AppUserModelID를 실제 창에 설정한다. 종료 전에 속성을 해제한다. 이전 코드에서 실제 창 아이콘이 정상인 경우도 확인돼, 과거 깃털 표시의 원인을 창 클래스만으로 확정하지 않는다.
- Windows의 큰·작은 아이콘 두 개를 프로세스 동안 재사용한다. 창 표시마다 Tk가 ICO를 다시 읽던 경로를 제거하고 재매핑 시 실제 HWND에 재적용한다. 자체 루트·자식 창을 20회 생성·표시·파괴한 진단에서 이전 코드는 GDI/USER 자원이 85/24에서 1282/423으로 늘었지만, 수정 후에는 28/5로 유지됐다. 실제 아이콘 픽셀과 작업표시줄 속성·정리 순서도 검사한다.
- 출처·작성자 기록에서 Windows 파일 점유를 재현했다. 검증된 임시 복사본을 최대 1초 동안 다시 교체하며, 매번 원본의 장치·파일 식별자·크기·수정 시각 및 링크 여부를 확인한다. 읽기 전용 파일은 임시 복사 전에 거절한다. 파일 점유·권한·읽기·쓰기·검증·시간 초과 등은 고정된 안전한 메시지로 안내한다.
- 파일 저장과 파일 안 메타데이터 기록은 별도 단계다. 후자가 실패해도 사진·영상 원본과 성공 다운로드 기록을 보존한다. 이전 실패는 파일 관리의 출처·작성자 기록 기능으로 다시 처리할 수 있다. 캡처만으로 지난 실패의 정확한 원인은 확정할 수 없다.

최종 전체 검사 943개: 939개 통과, 4개 생략(심볼릭 링크 권한 3개, opt-in 휴지통 실동작 1개). 처음 단일 프로세스 검사에서는 후반 GUI 테스트가 네이티브 접근 위반으로 종료됐다. 반복 아이콘 로딩의 자원 증가를 진단하고 제거한 뒤 전체 검사를 다시 통과했다. 해당 GUI 모듈 별도 17개와 메타데이터 관련 29개도 통과했다.

소스와 한글 경로에 새로 압축을 푼 실행 파일 자체 점검 통과. ZIP CRC·SHA256·실행 파일과 현재 소스 28개 모듈 및 entry.py 일치·7가지 아이콘 크기·개인정보와 임시 상태 제외 검사를 통과했다. 실제 사용자 X 계정과 저장 파일은 검사에 사용하지 않았다.

ZIP SHA256: `3526b55c8b4dc68bc646130a28d4b6679f2dea438c476cd09d007dc7d744dddf`

## Claude 검토

2026-10-14. Codex의 `d7d43de`(작업표시줄 아이콘·메타데이터 잠금 재시도)를 검토했습니다. 버전은 1.0.0 그대로이며 빌드·배포는 하지 않았습니다.

### 검토 결과

- 작업표시줄 속성: `IPropertyStore` 함수 순서(GetValue 5·SetValue 6·Release 2), `PKEY_AppUserModel_*` GUID와 번호 2–5, PROPVARIANT 크기(64비트 24바이트·32비트 16바이트), 재실행 속성을 ID보다 먼저 쓰는 순서가 Microsoft 문서와 맞습니다. 메인 창 닫기(`App.close`)·예약 실패 알림·자체 점검이 모두 감싼 `root.destroy`를 거쳐 속성을 지운 뒤 창을 없앱니다. 자식 창은 `<Map>` 바인딩으로 같은 아이콘을 받습니다. 고칠 문제는 없었습니다.
- 출처 기록 재시도: 공유 위반(32·33)과 읽기 전용이 아닌 ‘액세스 거부’만 최대 1초 다시 시도하고, 매번 원본의 장치·파일 ID·크기·수정 시각과 링크 여부를 다시 확인합니다. 전체 시간 제한도 지킵니다. 읽기 전용 파일은 임시 복사 전에 거절해 지우지 못하는 임시 파일이 남지 않습니다. 고칠 문제는 없었습니다.
- 문제 (안내): 저장 중 로그에는 실패 이유가 붙지만, 개발 안내가 재시도 방법으로 안내하는 **파일 관리 → 파일에 출처·작성자 기록**의 완료 안내에는 개수만 나왔습니다. 다른 프로그램이 파일을 계속 쓰고 있어 다시 실패해도 이유를 알 수 없었습니다.

### 수정

- `HistoryWindow._backfill_worker`가 실패 결과의 이유 코드를 세고, 완료 안내에 가장 많은 이유를 `metadata.failure_message`의 고정 문구로 붙입니다. 한 종류면 ‘실패 이유’, 여러 종류면 ‘가장 많은 실패 이유’로 표시합니다. 미지원 형식은 지금처럼 개수에만 포함합니다. 모르는 코드는 일반 안내로 바꾸며 ExifTool 출력·경로는 표시하지 않습니다.
- 개발 안내의 출처 기록 재시도 설명을 맞췄습니다.

### 참고 (수정하지 않음)

- 링크 경로는 `_MediaChanged`로 거절해 ‘기록하는 동안 파일이 바뀌어’ 안내가 나옵니다. 지금 호출 경로(다운로드 작업·기록 창)는 링크를 미리 걸러 실제로는 닿지 않습니다.

### 검증

- 검토 환경은 Linux(Xvfb, Python 3.12, Tk 8.6)입니다. 실제 Windows 작업표시줄 속성·공유 잠금·GUI 자원 검사는 이 환경에서 생략되므로 Windows에서 다시 확인해야 합니다.
- 새 검사 1개: 여러 이유(가장 많은 이유 표시), 한 가지 이유, 모르는 코드, 미지원·성공만 있는 경우와 도구 문구 비노출. 수정 전 코드에서 실패하고 수정 후 통과했습니다.
- 전체 944개: 861개 통과, 41개 실패·오류, 42개 생략. 실패·오류 목록은 수정 전 943개 실행과 같으며 모두 Windows 전용입니다(`os.startfile`, Windows용 `ffmpeg.exe`, 휴지통 API, 하드링크, 창 관리자 없는 Xvfb의 포커스·창 크기). 관련 모듈(메타데이터·미디어·아이콘·기록 창)은 Windows 전용 1개 외 모두 통과했습니다.
- 실제 X 요청, 사용자 설정·로그인·기록·미디어 변경은 하지 않았습니다.

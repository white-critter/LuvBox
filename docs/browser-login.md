# X 로그인 연결

LuvBox 1.1.8의 기본 연결은 **브라우저 연결(확장)**입니다. **고급 연결 · 토큰 입력**은 대체 수단이며, 별도 앱 전용 창에서 새로 로그인하는 기능은 배포하지 않습니다.

1. 앱의 **X 연결**에서 사용할 Chrome·Edge·Firefox를 선택합니다. 앱은 선택한 브라우저로 설치 안내·X 열기·계정 연결을 진행합니다. 브라우저가 실제로 연 일반 프로필에 확장을 설치하고 X에 로그인해 두세요.
2. **X 계정 연결** 또는 **다시 연결**을 누릅니다. 앱과 확장의 코드가 같음을 체크하면 X 계정을 자동 확인합니다. 브라우저의 **@아이디 연결**, 앱의 **이 계정 연결 승인**을 차례로 눌러 완료합니다.
3. 처음 설치 도움말은 접어 둡니다. 연결 시작 후 약 8초간 확장 응답이 없으면 펼치며, 미설치로 단정하지 않습니다. 브라우저·프로필·확장 활성 상태를 확인하고 [확장 설치 안내](../assets/browser-extension/README.md)를 따릅니다.
4. 수동 토큰은 `auth_token` 값을 입력해 **토큰 보관**을 누릅니다. 연결창은 그대로 열어 두며, 저장 화면에서 본인 X 아이디를 확인합니다. 토큰 저장만으로 실제 X 인증이 확인된 것은 아닙니다.

연결 정보는 이 Windows 계정에 암호화해 저장합니다. 토큰·쿠키는 다른 사람에게 보내지 마세요. 확장 자동 설치·스토어 배포는 아직 제공하지 않습니다.

## 브라우저 연결 확장

이미 사용 중인 브라우저의 X 로그인을 다시 로그인하지 않고 연결합니다. 사용자 설치 안내는 [브라우저 연결 확장 안내](../assets/browser-extension/README.md)에 있습니다. Chrome/Edge 개발자 모드 또는 Firefox 임시 부가 기능으로 확장을 직접 설치해야 합니다. 스토어 서명 배포나 자동 설치는 제공하지 않습니다. Firefox 임시 설치는 재시작하면 사라집니다. Safari·비공개 창·Firefox 컨테이너·관리 정책으로 확장이 차단된 환경은 확장 연결을 지원하지 않습니다.

브라우저 선택은 `connection_browser`라는 지원 브라우저 ID만 일반 설정에 저장합니다. 탐색·선택 저장·설치 파일 준비는 UI 밖에서 처리하며, 선택 저장에 실패하면 이전 선택과 폴더를 유지합니다. 실행 경로는 고정된 지원 브라우저의 설치 위치에서 찾고, 프로필 파일이나 연결 명령의 기존 인수를 읽어 실행하지 않습니다. 기본 브라우저가 달라도 선택한 제품을 사용하며, 그 브라우저가 고르는 활성/기본 일반 프로필을 안내할 뿐 특정 프로필을 확인했다고 주장하지 않습니다.

확장 파일은 `%LOCALAPPDATA%\LuvBox\browser-extension\chromium` 또는 `firefox`에 복사합니다. 앱 업데이트 후 연결창을 한 번 열고 확장 관리에서 **새로고침**하여 확장을 **1.1.0**으로 갱신하세요. Firefox는 갱신된 임시 부가 기능을 다시 불러옵니다. 이전 **1.0.0** 확장의 최종 세션 전달 형식은 계속 받지만 중간 단계 표시는 지원하지 않습니다. 앱에 이미 저장한 계정은 그대로 사용할 수 있습니다.

## 확장의 계정 확인과 저장

`luvbox.browser_bridge.BrowserBridge`는 앱에서 연결 버튼을 누른 뒤에만 시작합니다. 앱이 먼저 `127.0.0.1` 임의 포트를 바인드한 후 선택한 브라우저를 엽니다. 확장은 연결 요청을 자신의 확장 페이지로 넘깁니다. 앱과 확장에 표시된 8자리 코드가 같음을 사용자가 직접 체크하면 계정을 자동 확인합니다. 계정 재확인은 **계정 다시 확인**으로 수행하며, 전송 승인과 앱의 최종 저장 승인은 명시적으로 유지합니다.

계정 확인에는 기존 로그인 프로필 안의 새 `https://x.com/home` 탭 하나만 사용합니다. 다른 사람의 프로필이나 오래된 X 탭에서 계정을 추정하지 않습니다. 본인 프로필 탐색 링크와 `twid`의 숫자 사용자 ID를 읽고, 탭 확인 전후 및 연결 직전에 로그인 쿠키가 같은지 검사합니다. 자동으로 만든 탭만 닫습니다. 브라우저 프로필 파일·다른 사이트 쿠키·X 비밀번호는 읽지 않습니다.

`BrowserSession`은 `auth_token`, `username`, `user_id`, `display_name` 및 저장 API용 `identity`를 반환합니다. 호출자는 취소 상태를 다시 확인하고 `login.save_authenticated_session(session.auth_token, session.identity, cancel=cancel)`로 저장합니다. 브라우저는 전달 결과만 표시하고 최종 암호화 저장 성공은 앱이 표시합니다. 이미 연결한 여러 계정의 선택은 앱의 계정 저장소가 담당합니다.

## 진행 상태와 사용 가능 여부

확장 1.1.0은 `extension_ready`, `checking_account`, `login_required`, `account_changed`, `account_error`, `awaiting_approval` 단계만 암호화해 앱에 전달합니다. 앱은 실제 응답에 따라 확장 확인·계정 확인·브라우저 승인·앱 승인을 구분하고 남은 시간을 표시합니다. 브라우저 연결과 앱 최종 승인은 각각 최대 180초 대기합니다. 로그인·추가 인증·계정 전환 뒤에는 확장의 **계정 다시 확인**으로 이어갈 수 있습니다. 설치나 브라우저·프로필을 바꿨다면 취소 후 새 연결을 시작합니다.

화면의 계정 상태는 다음을 구분합니다.

| 상태 | 근거 |
| --- | --- |
| 연결 정보 저장됨 (`saved`) | 로컬 암호화 연결 정보를 읽을 수 있음. 현재 X 인증 성공을 뜻하지 않음 |
| 브라우저 계정 확인됨 (`browser_confirmed`) | 확장에서 본인 계정을 확인하고 앱 저장을 승인함. 저장 API 접근은 아직 미확인 |
| X 목록 접근 확인됨 (`verified`) | 저장 중 인증이 필요한 Likes API의 정상 목록 응답 구조를 확인함. 공개 사진 다운로드 성공만으로 표시하지 않음 |
| 다시 연결 필요 (`reconnect_required`) | X API의 명시적 인증 거부 근거를 확인함. 기존 연결·파일·기록은 지우지 않음 |

일반 통신 실패, 요청 제한, 특정 게시물의 접근 거부는 연결을 일괄 만료시키지 않습니다. 알 수 없는 응답 형식을 성공으로 간주하지도 않습니다. 사용 가능 여부는 현재 실행에서 확인한 근거이며, 토큰 보관이나 예전 실행의 성공으로 영구 보장하지 않습니다.

## 확장의 로컬 전달 경계

- 임시 포트를 고른 뒤 닫고 재사용하는 단계가 없습니다. Windows에서는 `SO_EXCLUSIVEADDRUSE`를 바인드 전에 설정해 다른 `SO_REUSEADDR` 소켓의 포트 공유를 막습니다. 바인드 실패 시 연결을 중단합니다.
- 연결마다 256비트 무작위 비밀을 생성해 URL fragment로만 확장에 넘깁니다. 확장은 즉시 fragment를 현재 기록에서 제거합니다. 비밀과 X 토큰을 HTTP URL·요청 헤더·로그·응답에 넣지 않습니다.
- 앱이 종료되거나 취소된 뒤 다른 프로세스가 같은 포트를 열 수도 있으므로 로그인 쿠키를 평문 POST하지 않습니다. 확장은 WebCrypto AES-256-GCM으로 계정 데이터를 암호화합니다. 비밀과 정확한 로컬 수신 주소를 문맥에 포함한 SHA-256으로 암호화 키와 별도 HMAC-SHA-256 키를 각각 유도합니다. 요청에는 nonce·암호문·GCM 태그·HMAC만 담습니다. 앱은 상수 시간 HMAC 검증 후 기존 고정 의존성 `gallery_dl.aes`의 AES-GCM 검증 복호화를 사용합니다. 다른 포트·다른 연결 비밀로는 복호화할 수 없습니다.
- 중간 단계도 `/progress`에서 AES-GCM·HMAC으로 보호합니다. `/session`과 다른 경로 문맥으로 키를 유도하고, 허용된 단계·순번·개수를 제한해 잘못된 순번과 재전송을 거부합니다. 단계에는 계정·쿠키·토큰이나 임의 오류 문장을 넣지 않습니다. 중간 단계는 최종 세션을 소비하거나 대기 시간을 연장하지 않습니다.
- 수신 주소는 IPv4 loopback 하나이며 Host·경로·브라우저 확장 Origin을 검사합니다. 일반 웹페이지의 교차 출처 요청과 CORS preflight는 허용하지 않습니다. 중복 보안 헤더·청크 전송·잘못된 길이·8 KiB 초과 본문을 거부하고 요청 읽기 시간을 제한합니다. 정상 결과는 한 번만 받으며 기본 3분·최대 5분에 만료됩니다.
- 쿠키 승인 UI는 웹에서 접근 가능한 자원으로 노출하지 않은 확장 자체 페이지에 있습니다. localhost 페이지에는 승인 버튼이 없고, 확장 페이지의 실제 사용자 입력만 승인합니다. 다른 페이지·하위 프레임·외부 메시지를 통한 확장 호출을 받지 않습니다. 쿠키는 확장 background 메모리에만 잠시 유지하고 디스크에 저장하지 않습니다.

loopback TCP 자체는 상대 프로세스가 LuvBox임을 증명하지 않습니다. 앱과 확장의 연결 코드 비교가 사용자의 실제 앱 요청을 확인하는 단계입니다. 같은 사용자 권한으로 프로세스 메모리·브라우저 확장·앱 파일을 수정할 수 있는 악성코드까지 격리하는 설계는 아닙니다. 확장이 아닌 페이지가 쿠키 승인 버튼을 흉내 내도 확장의 쿠키 읽기·전달 함수를 실행하지 못하도록 승인 페이지를 분리했습니다.

## 검증과 남은 확인

`python -m unittest tests.test_browser_bridge -v`로 loopback 경계·취소·만료·암호화·포트 바인드·일회성 연결과 확장의 합성 API 동작을 검사합니다. 선택적으로 Playwright와 Chromium이 설치되어 있으면 합성 X HTML/쿠키를 사용한 실제 확장 통합 검사를 실행합니다. 실제 네트워크의 X 로그인은 하지 않습니다.

이전 클라우드 환경의 Chromium 154는 관리 정책 `ExtensionInstallBlocklist: ["*"]` 때문에 개발 확장을 로드하지 못했습니다. 이런 통합 검사는 사유를 표시하고 건너뛰며 정책을 바꾸지 않습니다. 2026-10-22 Windows에서는 사용자의 명시적 확장 승인, 실제 X 계정 아이디 자동 반영과 실제 앱 재시작 후 연결 유지를 확인했습니다. 합성 세션으로 실제 DPAPI 저장·계정 선택·취소·연결 해제·별도 프로세스 재시작도 검증했습니다.

1.1.5에서 사용하지 않던 별도 Chrome/Edge 새 로그인 코드(임시 프로필·DevTools 파이프)를 제거했습니다. 연결 방법은 위 두 가지뿐입니다.

## 확장 없는 로그인 창의 타당성 확인

1.1.8 작업에서는 Qt WebEngine의 격리된 합성 페이지와 가짜 쿠키로 쿠키 수신 기능을 오프라인 확인했습니다. 실제 X 접속·로그인·2단계 인증·계정 전환·재시작 후 유지 성공을 뜻하지 않으며, 실험 코드를 제품 진입점이나 배포 런타임에 넣지 않았습니다. 기존 브라우저의 로그인 정보를 가져오는 방식도 아닙니다.

이 대안을 제품에 넣으려면 실제 X 로그인 호환성, 추가 인증, 취소·종료 정리, 별도 세션의 암호화 보관과 런타임·배포 비용을 먼저 확인해야 합니다. 현재 배포는 기존 확장과 토큰 방식을 유지합니다.
